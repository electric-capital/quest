# Voice Input

## Overview

Voice input lets a user **dictate a prompt** instead of typing it. A microphone button in the chat composer captures speech in the browser and the transcript lands in the textarea for the user to edit before sending. Nothing about the message path changes: the conversation only ever sees the text the user sends. The button has two modes, chosen by the server:

- **Live dictation** (when the server has a local speech model): the browser streams the microphone over `WS /app/api/transcribe/live` and the text **appears in the textarea while the user is still talking**, decoded by a [Qwen3-ASR](https://huggingface.co/Qwen/Qwen3-ASR-1.7B) checkpoint running inside the Quest process. Nothing leaves the machine.
- **Clip mode** (otherwise): the browser records a whole utterance with `MediaRecorder`, uploads it to `POST /app/api/transcribe`, and a Gemini model in the deployment's own Vertex AI project transcribes it.

`GET /me` reports the mode as `voice_input_live`; the composer picks the live hook when it is true and the browser can stream audio, the clip recorder otherwise. Both keep the audio inside the deployment: no third-party speech service, and never the browser's cloud-routed Web Speech API, which would stream it to the browser vendor and conflict with the self-hosted, no-egress stance of the rest of the frontend (see [frontend.md](frontend.md)). Both produce plain text, so they work with every chat model; passing audio straight to the model as an attachment would work on Gemini only and would leave the persisted user message empty. Clip mode needs no new secret (every deployment already carries Vertex credentials for chat inference); live mode needs no credentials at all, only the model weights and CPU time.

The whole feature sits behind the admin **`voice_input` feature gate** ([feature-gates.md](feature-gates.md)), off by default and per-user capable. The gate **cannot be turned on while neither mode can run** (no Gemini Vertex model configured and no local speech model); the admin endpoint refuses with 400 `feature_unavailable` and the Settings toggle stays disabled with the reason shown.

## Live Dictation

### Why not qwen-asr's streaming API

The `qwen-asr` package ships a streaming mode, but only on its vLLM backend, which needs a CUDA GPU. The transformers backend runs on any machine, and a 1.7B model in bfloat16 decodes a one-second step in about a second on a 16-core CPU (measured on a Xeon with AMX: 0.8 to 1.1 s per step with 15 s of audio in the segment, the whole model loading in a few seconds from the page cache). So `chat/live_transcription.py` re-implements the same algorithm on the transformers backend:

- Audio accumulates into a **segment**. Every `STEP_SECONDS` (1 s) of new speech, the whole segment is decoded again with the previous output, minus its last `UNFIXED_TOKENS` (5) tokens, fed back as a prompt prefix. The model only has to produce the tail, and the text shown so far cannot change beyond those few tokens.
- The first `UNFIXED_CHUNKS` (2) steps of a segment use no prefix, so a wrong guess on a short fragment (the language included: half a second of English is read as Chinese surprisingly often) is discarded rather than locked in. A segment's first decode also waits for `MIN_FIRST_DECODE_SECONDS` (1.2 s) of audio.
- A segment ends on `SILENCE_SECONDS` (0.8 s) of trailing silence, at `MAX_SEGMENT_SECONDS` (30 s, cut at the quietest frame of the last `CUT_SEARCH_SECONDS`), or when the client stops. Its last decode is **final**: the text is committed and the next segment starts from nothing, which keeps every decode's audio bounded and the prefix short. The raw output keeps the model's `language X<asr_text>` header for the prefix and is parsed into text with the package's own `parse_asr_output`.
- Segment boundaries come from an energy detector on 20 ms frames with an adaptive noise floor (`_EnergyGate`: the floor drops to any quieter frame at once and rises slowly; speech must exceed both `MIN_SPEECH_RMS` and `SPEECH_OVER_FLOOR` times the floor). Silence is never decoded, so a quiet room costs no CPU and the model is never asked to invent speech for it; leading silence beyond a `PRE_ROLL_SECONDS` pre-roll is dropped and trailing silence trimmed to `TAIL_SILENCE_KEEP_SECONDS` before the final decode. The browser opens the microphone with echo cancellation, noise suppression and auto gain on, which keeps the detector's fixed floor honest across microphones.
- Decoding runs on one worker thread per process (`_executor`), so concurrent sessions share the model and queue behind each other; the socket admits at most `MAX_LIVE_SESSIONS` (3). The weights load once (`LocalASREngine.ensure_loaded`, in the same worker so a load never races a decode): at startup when `local_asr.preload` is true (the default; `preload_if_configured()` from the FastAPI lifespan), otherwise on the first session, which sees a `loading` event meanwhile. A failed load is remembered rather than retried per session, and surfaces as the gate's `unavailable_reason`.

### Configuration

The `local_asr` section of `server_config.json` (`config/server_config.py` defaults; `server_config.example.json` documents it): `model` (a Hugging Face repo id or local directory; empty = live dictation off, clip mode unaffected), `device` (`cpu`, `cuda:0`), `dtype` (`bfloat16`), `threads` (CPU threads for decoding, 0 = torch's default) and `preload`. `QUEST_LOCAL_ASR_MODEL` overrides `model` from the environment. The packages are the `asr` extra of `pyproject.toml` (`qwen-asr` + `torch`, with `torch` pinned to the CPU wheel index on Linux so a server without a GPU does not download the CUDA build; a GPU deployment points `[tool.uv.sources]` at the matching CUDA index): `uv sync --extra asr`, which `run.py` runs by itself when `local_asr.model` is set. The weights come from the Hugging Face cache (`local_files_only` first, then a download), so an air-gapped deployment pre-populates the cache. See [development.md](../setup/development.md#local-speech-model-live-dictation).

### Socket protocol

`WS /app/api/transcribe/live` (`chat/routes/transcribe_live.py`), authenticated like the realtime socket (session cookie or `?api_key=`, `chat/realtime/ws_auth.py`), then the per-user gate, then availability and the session cap. Refusals are one `{"type": "error", "code", "message"}` event followed by a close with a `CLOSE_*` code (4401 unauthenticated without an event, 4403 `voice_input_disabled`, 4503 `live_transcription_unavailable`, 4509 `busy`, 4400 `bad_language`, 4413 `limit`, 4500 internal). Then:

1. `{"type": "loading"}` while the weights load, `{"type": "ready"}` when the server will take audio. An optional `?language=` query forces the language (`LANGUAGES`); default auto-detect.
2. The client sends **binary frames of 16 kHz mono little-endian PCM16** (about five 200 ms frames a second; at most `MAX_FRAME_BYTES` each, `MAX_SESSION_SECONDS` of audio per session). The server answers with `{"type": "partial", "text"}` (the current segment so far, replacing the previous partial) and `{"type": "final", "text"}` (a finished segment; empty ones send nothing).
3. The client sends the text frame `{"op": "stop"}` when the microphone is released; the server finalizes the open segment, sends `{"type": "done"}` and closes normally. A socket that just disconnects is abandoned (whatever was not final is dropped). A decode failure mid-session is one `error` event (`decode_failed`).

### Browser side

`frontend/src/hooks/useLiveDictation.ts` runs the state machine `idle -> connecting -> listening -> finishing -> idle`. `start()` opens the socket and the microphone together (the ready handshake, possibly a model load, overlaps the permission prompt), then builds the capture pipeline: an `AudioWorklet` loaded from a blob URL (`utils/pcm.ts` `CAPTURE_WORKLET_SOURCE`, so no separate build artifact) forwards float32 frames to the main thread, where `FrameBatcher` resamples them to 16 kHz (box-averaging for integer ratios such as 48 kHz, linear interpolation otherwise) and `floatToPcm16` packs `FRAME_SAMPLES` (200 ms) frames for `WebSocket.send`; a `ScriptProcessorNode` is the fallback where worklets are missing. The frames' RMS feeds `inputLevel` for the level meter. `committedText` grows on `final`, `partialText` is replaced on `partial`; `stop()` flushes the sub-frame remainder, releases the microphone, sends `stop` and waits (`FINISH_TIMEOUT_MS`) for `done`, then `onFinished(committedText)` fires. `stop()` during `connecting` is a cancel; `cancel()` tears everything down silently. The microphone itself is opened by `openMicrophone` shared with the clip recorder (default device by id, see Constraints), and failures carry the same `VoiceInputDiagnostics` report (stages `connect_live` / `live_dictation`).

In `Composer.tsx` the live transcript is mirrored into the textarea as `draft + committed + partial` (`joinTranscript`), with the draft captured when dictation starts. The textarea is **read-only while dictating** (class `dictating`, a faint tint and a red caret): typing would be overwritten by the next update, and on a phone a read-only field does not pop the keyboard. Enter and Send still work mid-dictation: the dictation is stopped and the draft is sent as soon as `done` lands the final text (the same `sendAfterTranscriptionRef` mechanism as clip mode). The mic button, level meter, timer and placeholders are shared between the two modes through `micState`.

## Flow

1. Admin turns on **Settings > Features > Voice input** (optionally for specific users). `PUT /admin/feature-gates/voice_input` runs `voice_input_availability()` first and refuses when neither a Gemini Vertex model nor a local speech model is configured.
2. `GET /me` lists `voice_input` in `enabled_features` and says whether live mode is on (`voice_input_live`); `Composer.tsx` shows the mic button if the browser can capture audio here.
3. Click, live mode: `useLiveDictation.start()` opens the socket and the microphone (amber "connecting" state until the server says `ready` and audio flows), then streams PCM frames; `partial` / `final` events update the read-only textarea as the user talks. Click again (or `MAX_LIVE_SECONDS`): `stop()` releases the microphone and waits for `done`, and the final text replaces the live one.
4. Click, clip mode: `useVoiceRecorder.start()` asks for the microphone, starts `MediaRecorder`, and shows the amber "starting" state until the analyser hears the microphone actually deliver audio (or 3 s pass). Click again (or 120 s): `stop()` assembles the Blob and calls `onRecordingComplete`; `transcribeAudio()` POSTs the clip; `chat/routes/transcribe.py` gates, validates and calls `chat/transcription.py`, which picks the model and runs `GeminiProvider.transcribe_audio()`.
5. In either mode a failure at any step calls `onError` with a message and the run's diagnostics; the composer shows the message as a tappable notice whose details view holds the full report.
6. The transcript lands in the textarea. The user edits and sends as usual; the conversation loop never sees the audio. Pressing Send (or Enter) while still dictating skips the edit step: the dictation stops, and the draft plus transcript is sent as soon as the final text arrives.

## Constraints

- **Never open the microphone with a bare `{audio: true}`.** On macOS, Chrome resolves an unconstrained audio request by waking every input device it could pick from. With an iPhone nearby offering Continuity Camera, that connects the phone -- the phone chimes and audio takes a couple of seconds to arrive -- even though the built-in microphone is the device that ends up used, and the link drops again after a short idle so the next recording pays it again. Requesting `deviceId: {exact: 'default'}` opens only the default device and does neither (verified from the DevTools console: the bare form wakes the phone, the exact form does not). Browsers without Chrome's `default` alias reject the constraint and get the bare form as a fallback. Recognise that rejection by the error's `name` read duck-typed (`errorName()`), never with `instanceof DOMException`: WebKit's `OverconstrainedError` is a class of its own, and an instanceof guard made every iPhone fail with "Could not start recording" before the bare request was tried (found via the first screenshot report from staging, Oct 2026).
- **Microphone start-up lag.** `getUserMedia` resolving and `MediaRecorder.start()` returning do not mean audio is flowing: some devices take a moment to deliver samples (Bluetooth headsets switching to their hands-free profile take one to three seconds), and everything spoken before that is silence in the clip. The `starting` state exists so the user is told to wait rather than shown a running timer.
- **`starting` must always end on its own.** Nothing after `MediaRecorder.start()` may gate the transition to `recording` on a promise the browser is free to leave pending: iOS Safari does exactly that with `AudioContext.resume()` when it decides the page may not start audio. The give-up timer is armed first and the resume is raced against its own timeout; the level meter is optional, the recording is not.
- **Failures must be readable on a phone.** There is no console on an iPhone, so a voice-input failure is reported twice: a short notice, and the full report behind it (`NoticeDetailsModal`) that the user can screenshot or copy and paste into a debugging session. The report must stay terse enough to fit one screen -- relative timestamps, one line per step, no stack traces -- and must not include the transcript or any audio. Keep the trace lines meaningful: when adding a step to the hook, log it.
- **Live dictation is CPU-bound and serialized.** One decode thread per process; a second concurrent dictation roughly doubles both users' latency, and `MAX_LIVE_SESSIONS` refuses a fourth. A machine without AVX-512/AMX (or a bigger checkpoint) may fall behind real time: steps then take longer than the audio they cover, partials lag further behind speech, but nothing is lost, since every step re-reads the whole segment. Watch the per-session INFO lines (decodes and segments) and the step time if dictation feels slow; `local_asr.threads` caps the CPU it takes from the rest of the server.
- **Segmenting on energy, not on words.** Speech is anything above the adaptive floor, so a keyboard burst or a cough opens a segment (the model usually answers `language None` and nothing is committed), and a very long breath pause ends one mid-sentence. Punctuation and capitalization across a segment boundary come from the model seeing each segment alone; the prefix is never carried across segments.
- **Live mode is read-only text until `done`.** The textarea cannot be edited while dictating; the draft typed before the dictation is kept in front of the transcript. A cancel (composer lock, conversation switch) drops the uncommitted partial but leaves committed text in place.
- **Secure context.** `getUserMedia` only exists on `https://` origins and `localhost`. A plain-http dev instance reached by IP or an `/etc/hosts` hostname ([development.md](../setup/development.md)) hides the button; test through an SSH tunnel to `localhost`, an HTTPS front ([production.md](../setup/production.md) "Serving over HTTPS"), or Chrome's `chrome://flags/#unsafely-treat-insecure-origin-as-secure`.
- **Clip mode is Gemini only.** Anthropic and OpenRouter models take no audio input, so a Vertex deployment with every Gemini model disabled and no local model cannot enable the gate. Instance (OpenRouter) Gemini models are not used either.
- **Length limits.** Clip mode: 120 s / 6 MB per clip, enforced in the browser (auto-stop) and again on the server; longer dictation is several clips, each appending to the draft. Live mode: `MAX_SESSION_SECONDS` (10 min) of audio per socket, the browser stopping at `MAX_LIVE_SECONDS` just under it.
- **Not recorded in cost analytics.** Transcription calls do not belong to a conversation, so they are not written to the `llm_calls_gemini` table ([database.md](database.md)); each clip call is logged at INFO with model, size and duration, each live session with its decode and segment counts.
- **Untrusted speech.** The clip-mode prompt tells Gemini to transcribe verbatim and never act on instructions spoken in the clip; the local model is a pure recognizer with no instruction channel. Either way the result is user-editable text, not a message, so a spoken injection has no more reach than a typed one.
- **Slack, Telegram and other inbound channels** do not use this path: their message handlers drop or never fetch audio ([slack-socket-mode.md](slack-socket-mode.md)).
