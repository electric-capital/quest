# Memory Suggestions

## Overview

The model can propose a memory about the user **without interrupting the conversation**: the `suggest_memory` dynamic tool registers a pending row and returns at once, the turn keeps going, and the web UI shows a "N suggested memories" bubble above the composer. Clicking the bubble opens a panel over the conversation where the user edits, accepts (creating a `memories` row) or dismisses each suggestion. Nothing is saved until the user accepts. The same rows, across every conversation and together with project-memory and doc note suggestions, make up the inbox's Memories tab (see [The Inbox's Memories Tab](#the-inboxs-memories-tab)), whose unanswered count is part of the sidebar inbox badge and of the Slack reminders.

The rows have a second writer: a dream ([Dreaming](dreaming.md)), the offline review of the user's memory store, registers its proposals as suggestions with `source` `dream` and no conversation, so they appear in the inbox only. A dream can also propose retiring a memory outright: an **archive-only** suggestion has no `content`, and accepting it archives `replaces_memory_id` without creating a memory (an edit is refused with 400 `invalid_memory`; the accept response then carries `memory: null`).

This sits beside the blocking `create_memory` action request (see [Action Requests](action-requests.md)): an explicit "remember that ..." still opens the Approve / Revise / Stop card so the user confirms at once; unprompted observations go through the suggestion path. The system prompt tells the model which to use and what is worth suggesting. Facts about a project rather than the user go to [Project Memories](project-memories.md), which reuse this machinery with their own bubble; proposed changes to a Quest Doc's notes have their own twin ([Doc Note Suggestions](doc-notes-review.md)).

The review UI serves all three kinds (personal memories, project memories, doc notes): one row component, one bubble per kind and the inbox tab, none of them gated. Doc note rows are also reviewed in the doc viewer's Notes panel; what is particular to them is in [Doc Note Suggestions -- Frontend](doc-notes-review.md#frontend).

## Key Files

- `db/models.py` -- `MemorySuggestion` / `MemorySuggestionStatus` / `MemorySuggestionSource`: the `memory_suggestions` table (`source` conversation / dream, the proposing `conversation_id` or the `dream_run_id`, `content` -- null for archive-only -- the model's `reasoning`, an optional `replaces_memory_id`, `status` pending / accepted / dismissed, the `memory_id` created on accept). Rows cascade with their user and, when they have one, their conversation; the memory and run references are `SET NULL` on delete. Created by `alembic/versions/c7e2a9b4d1f8_add_memory_suggestions.py`, reshaped by `b4e8d2c7a1f3_add_dreaming.py`.
- `db/memory_suggestion_store.py` -- create / list / count / accept / dismiss, all user-scoped. `create_suggestion()` takes the optional conversation, `source` and `dream_run_id`, and refuses an archive-only row that names no memory. `list_pending()` joins the replaced memory so each row also carries `replaces_content` (its current text, or null). `accept_suggestion()` claims the row (`pending` -> `accepted`), inserts the memory (optionally with the user's edited text) and archives the replaced memory in one transaction -- for an archive-only row it inserts nothing, refuses an edit, and returns `memory` None; a second accept or dismiss raises `SuggestionAlreadyResolvedError`. `count_pending_for_user()` takes an optional `source` (the dream pacing counts only dream rows). The per-conversation pending cap is `MAX_PENDING_PER_CONVERSATION`. The per-user queries behind the inbox -- `list_pending_for_user()`, `count_pending_for_user()`, the keyset-paged `list_resolved_for_user()` with its `(resolved_at, id)` cursor helpers and the cross-user `list_pending_summaries()` -- have twins in `db/project_memory_suggestion_store.py` and `db/doc_note_suggestion_store.py`, which share the cursor; `conversation_context()` gives every inbox row that has a conversation its conversation.
- `chat/memory_inbox.py` -- merges the three kinds (personal, project and doc notes) for the inbox: `list_pending()` (oldest first, each row tagged `kind` and carrying `conversation_title` / `project_id` / `project_name`, all null for a dream's row), `list_resolved()` (one keyset page across the three tables), `count_pending()` and the per-user `list_pending_summaries()` the Slack reminder counts. A `doc` row is the doc notes review row ([Doc Note Suggestions -- Counts, Inbox and Report](doc-notes-review.md#counts-inbox-and-report)). None of it is gated.
- `chat/memory_suggestions.py` -- the tool body `register_suggestion()` with its duplicate guards (`already_saved` when an active memory holds exactly the text, `already_suggested` when the conversation already has it pending, a structured error at the cap), plus `accept_suggestion()` / `dismiss_suggestion()` wrappers; every change publishes `memory_suggestions_changed` via `publish_changed()`.
- `chat/llm/tool_schemas.py` -- the `suggest_memory` spec in `TOOL_CALL_REGISTRY` (`content`, optional `reasoning` and `replaces_memory_id`). Not `mutating`, not public-allowlisted.
- `chat/gemini_api/tool_dispatch.py` -- `_tool_suggest_memory` refuses sub-agent, cross-user subagent, inference-API and sandbox-script runs with a structured error (the backstop behind the prompt exclusions); the handler itself is `_handle_suggest_memory` in `chat/gemini_api/tool_handlers/memory.py`.
- `chat/gemini_api/system_prompt.py` -- the "Memories" rule (which path to use, what to suggest, search first) and the example call; the tool is excluded from routine, sub-agent, cross-user subagent and inference prompts. `chat/system_skills/catalog.py` (`_memory_content`) carries the full guidance in `system:memory`.
- `chat/memory_routes.py` -- `GET /app/api/conversations/{id}/memory-suggestions` (pending, oldest first; 404 for a conversation the user does not own), `POST /app/api/memory-suggestions/{id}/accept` (optional `content` override; 400 `invalid_memory`, 409 `suggestion_resolved`, 404 `suggestion_not_found`) and `POST .../dismiss`; plus the inbox routes `GET /app/api/memory-inbox/counts` (`{user, project, doc, pending_count}`), `GET /app/api/memory-inbox/pending` and `GET /app/api/memory-inbox/resolved?cursor=&limit=` (`{suggestions, next_cursor}`, null cursor at the end; 400 `invalid_cursor`).
- `chat/routes/conversations.py` -- `GET /conversations/{id}` carries `pending_memory_suggestions` so the bubble is right on load.
- `chat/realtime/events.py` -- `make_memory_suggestions_changed(conversation_id, pending_count, total_pending)`, a per-user global (listed in the FE's per-user-global allow-list in `frontend/src/services/PersistentWebSocket.ts`); `total_pending` is the user's pending count across all conversations, for the inbox badge and tab label. A dream's batch publishes it once with `conversation_id` null and `pending_count` 0: no bubble moves, only the inbox.
- `frontend/src/components/MemorySuggestionRow.tsx` -- one pending suggestion under review, shared by the composer panel, the inbox and the doc viewer's Notes panel; the header comment gives its three kinds and what each row shows. An archive-only row (a dream retiring a memory) has no textarea: it shows the memory it retires, struck through, under "Archives this memory", and Accept is always enabled. The replacement diff follows the user's edits (`frontend/src/utils/wordDiff.ts`), and the exported `DocTitleLink` is also the inbox source line's doc link.
- `frontend/src/components/docNoteReview.ts` -- the review helpers every surface shares: the edited text an Accept sends and, for doc rows, the accept options and the stale re-base (its header comment).
- `frontend/src/components/MemorySuggestions.tsx` -- the bubble and the review panel of one kind; the header comment gives each kind's endpoints and wording, and why rows resolved in the panel are left out of every later list read. `MemorySuggestionsBar` renders the three bubbles side by side, each hidden while its count is zero; `ChatPanel.tsx` renders the bar as a direct child of `.chat-panel` (the phone rule in `MemorySuggestions.css` relies on it), above the expensive-resume card and the composer.

- `frontend/src/store/conversationStore.ts` / `frontend/src/hooks/useConversation.ts` -- `pendingMemorySuggestions` and its project and doc note twins, seeded from the GET payload and replaced by every event's count; the open panel re-fetches its list when the count changes.

## Flow

1. The model calls `tool_call(tool_name="suggest_memory", arguments={content, reasoning?, replaces_memory_id?})`; `register_suggestion()` runs the guards, inserts the row and publishes the new pending count. The tool result (`status: "suggested"`, `suggestion_id`, `pending_count`) comes back immediately and the turn continues.
2. Every tab showing the conversation updates the bubble from the event; a fresh load reads `pending_memory_suggestions`.
3. The user opens the panel (`GET .../memory-suggestions`), optionally edits a row, and accepts or dismisses it. Accept creates the memory (and archives the replaced one); both publish the event, so other tabs and the bubble follow.

## The Inbox's Memories Tab

The inbox (`RequestsView`, see [Action Requests -- Frontend Components](action-requests.md#frontend-components)) has a Memories tab at `/inbox/memories` beside the Requests tab at `/inbox`; both paths are served by the SPA routes in `quest.py` and keep `showRequestsView` set in `App.tsx`. `MemoryInbox.tsx` renders:

- **Open suggestions** -- the user's pending suggestions, oldest first, from `GET /app/api/memory-inbox/pending`. Each is a `MemorySuggestionRow` with a source line naming its kind, its conversation (a link to it) and project, or "From a memory review" for a dream's row, which has no conversation, and, for a doc row, its doc ([Doc Note Suggestions -- Frontend](doc-notes-review.md#frontend)). Accept / Dismiss call the kind's own endpoints (`KIND_API`); a resolved row moves to the top of the reviewed list at once, and a 409 `suggestion_resolved` from another tab just drops it. The list is re-read on each of the three `*_suggestions_changed` events; the `MemoryInbox.tsx` header comment gives which read wins and the race it closes.
- **Recently reviewed** -- accepted and dismissed suggestions, newest first, from `GET /app/api/memory-inbox/resolved` in pages of `RESOLVED_PAGE_SIZE`, each with its source line. An `IntersectionObserver` under the list loads the next page as it scrolls into view, with a Load more button where the observer is unavailable.

Both lists leave out rows of a kind with no `KIND_API` entry (a kind the server adds before the tab knows it) rather than show buttons that cannot work. A reviewed page can therefore come back with none of its rows kept; while its cursor says more follow, the list does not show its empty state.

The tab label in `RequestsView.tsx` and the sidebar badge (`frontend/src/components/sidebar/RequestsBadge.tsx`) take their counts from `usePendingSuggestionCounts()`: seeded from `GET /app/api/memory-inbox/counts`, then each kind's event's `total_pending`; the hook's header comment gives how a late seed or fetch never overwrites a newer value. Its `suggestionCountKind()` is the one event-to-kind mapping, also behind the inbox's re-reads. The tab label shows the sum of the three kinds, and the badge adds it to the open action requests. The Slack reminder counts the same pending suggestions (see [Slack Pending-Request Notifier](slack-pending-request-notifier.md)).

The resolved list pages the three tables with one `(resolved_at, id)` keyset cursor; the `list_resolved()` docstring says why the merge never skips or repeats a row and when it costs one trailing empty page.

## Guidance the model gets

The prompt and the `system:memory` skill combine the memory rules of other harnesses: suggest only facts that are stable over time, likely to matter again and clearly about the user (role, expertise, preferences, working and writing style; corrections and confirmed approaches with the reason; ongoing work, goals and constraints with absolute dates; URLs, dashboards and tickets), never one-off task details, temporary states, anything derivable from the workspace or docs, or sensitive information unless the user asked. The model must `memory_search` the topic first, skip facts a memory already covers, and pass `replaces_memory_id` when a saved memory is outdated. One self-contained fact per call, a handful per conversation, and the reply must not restate the suggestion or claim it was saved.

## Design Decisions

- **Side channel, not a card.** The blocking card interrupts the user for every proposal; a review panel they open when they like keeps proactive suggestions cheap to ignore. The explicit-request path keeps the card because the user expects immediate confirmation there.
- **One inbox for every kind.** Suggestions left behind in closed chats would otherwise be found only by reopening each chat; the inbox routes list them all, personal, project and doc notes together, because to the user they are the same chore. The three tables stay separate (they write different stores and publish different events); the merge is a thin layer over per-user queries.
- **One row component for every kind and surface.** The bubble, the inbox and the doc viewer's Notes panel render the same `MemorySuggestionRow`, and the doc rows share their accept and re-base helpers, so a doc note is reviewed the same way wherever it is answered; a doc-specific row per surface was rejected as three copies that would drift.
- **Exact-text duplicate guards only.** Semantic de-duplication is the model's job (search before suggesting); the server guards are cheap exact matches that prevent the obvious repeats without an extra model call.
- **Replace, not edit.** Memories have no agent-side edit tool. A suggestion with `replaces_memory_id` archives the old memory on accept, so corrections never leave two conflicting facts active.
- **Top-level only.** Sub-agents, cross-user subagents, inference runs, scripts and public-project conversations never reach the tool; routine runs do not see it (a canned task is not a conversation with the user).
- **One table for both writers.** A dream's proposals are ordinary suggestions with a `source`, so the inbox, the badge, the Slack reminders and the accept / dismiss routes serve them unchanged; archive-only rows are the one new shape, because a clean-up must be able to retire a memory without inventing a replacement.
