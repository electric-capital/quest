# Quest Tables Frontend

## Overview

The UI at `/tables`: the sidebar Tables blocks, All Tables with its New Table dialog, the viewer with its header menu, filter bar, server-sorted and paged grid, footer, Columns panel (the schema editor) and History drawer, and the previews of the three table approval cards. It follows the [Quest Docs frontend](quest-docs.md#frontend) file for file (`useTables` is `useDocs`, `TablesListView` is `DocsListView`, `TableHistory` is `DocHistory`, and so on), so this doc covers only the files and the rules that span them; each component's header comment describes its own behaviour. The routes it calls are [Quest Tables API -- HTTP Routes](../api/tables-api.md#http-routes), the card payloads [Quest Tables API -- Action Requests](../api/tables-api.md#action-requests), the events [Quest Tables -- Realtime Events](quest-tables.md#realtime-events). Paths are under `frontend/src/` unless noted.

## Routes and State

`/tables` is All Tables, `/tables?project=<id>` the same view filtered to one project, and `/tables/<id>` the viewer, which also takes `?filter=<JSON>&sort=<JSON>`. As for docs, the URL is the only state: `App.tsx`, `MobileShell.tsx` and the Sidebar run `parseTablesRoute()` on every render, and a tables route is a full main-pane takeover with no RightPanel. While `tables` is missing from `enabledFeatures` the route renders `TablesGateClosed` and nothing is fetched, and the Sidebar mounts no Tables blocks. `MobileShell` closes its drawers when the route arrives at a list or a table, but not when only the viewer's filter or sort changes. `serve_spa_tables` in `quest.py` serves the deep links ([Quest Tables API -- SPA Routes](../api/tables-api.md#spa-routes)).

## Lists

The sidebar shows the user's own user tables and, while drilled into a project, that project's tables, each block under its Docs block and capped at `SIDEBAR_TABLE_LIMIT`. All Tables combines the same three sources as All Docs, because `GET /tables` has no cross-project stream: "Your tables" and "Shared with you" are two server-paged `useTables` streams, and each project gets a group from `useProjectTablesIndex`, archived projects included. The project filter shows only that project's stream. New Table opens `NewTableDialog` ([Schema Editor](#schema-editor)), which `TablesListView` owns unless its host passes `onNewTable`. With no tables at all, or none in the filtered project, the view says in a line what a table is for and offers the same dialog; the sidebar block points at asking Quest. A failed load never reads as "no tables": both say it failed.

## Viewer

`TableViewer.tsx` is keyed by table id; its only own state is the grid offset, which is not in the URL, so a link opens on the first page. Rules that span its parts:

- **Filter and sort live in the URL.** `TableFilterBar` turns the `filter` param into one chip per AND-ed condition, by column name; it and the grid's sort headers report every change back, and the viewer navigates (with `replace: true`) to the encoded DSL (`tableViewerSearch()`), so a filtered, sorted view is a link and the params are the rows API's own JSON. A filter the bar cannot show as chips (`or`, `not`, nesting, an op or value it does not offer) stays applied as one "Custom filter" chip, never dropped. A server filter refusal is shown on the bar, on the chip its `path` points at. The bar's caps in `utils/tableFilter.ts` hand-mirror the `TABLE_FILTER_*` and `TABLE_SORT_MAX_KEYS` constants in `chat/tables/constants.py`.
- **Stale column names are not sent.** A sort key or filter naming a column the loaded schema lacks (dropped or renamed) is left out rather than sent into a 400 `unknown_column`, and a note under the bar says so, with a Clear button.
- **Grid.** One page of `TABLE_GRID_PAGE_SIZE` rows (the server's `TABLE_GRID_MAX_LIMIT`), sorted server-side; a header click cycles its column through ascending, descending and none and replaces the whole sort with that one key (a linked sort of up to three keys is still sent in full, with only the first key's arrow shown); a sort or filter change returns to the first page, and a total that shrinks below the offset steps back to the last page. An empty result says how rows get in (asking Quest in a chat, unless the viewer's rows verdict is `denied`; the page has no row editing) or, under a filter, offers Clear filter.
- **Cells** (`utils/tableCells.tsx`). Numbers show at the column's precision by string arithmetic rounding half-even like the server, with no `Intl` and no separators, so the grid shows exactly the digits the model and the CSV see in every locale. A url becomes a link (`rel="noopener noreferrer"`) only when it parses as http(s), otherwise it renders as text. A null renders as a muted NULL marker, distinct from an empty string.
- **Header actions follow the detail's `access` flags** (`TableHeader.tsx`), never a role recomputed client-side. Columns opens the Columns panel for everyone (read-only without `can_edit_schema`), History the drawer for editors. Share is a disabled item, since the viewer wires no share dialog; its reason is visible text tied to it with `aria-describedby`, because a `title` is neither shown on touch screens nor read out on a disabled button. The require-approval switch sends no `expected_updated_at`, because row writes move `updated_at` and switching approval on to stop an agent mid-write must not fail as stale. Rename sends it, and on a `stale_update` whose current row still has the old title (only rows moved) retries once against the current token.
- **Header keys.** While the menu is open, single keys run its items as in DocHeader (the keys are in `TableHeader.tsx`'s header comment). A key acts only on an item that is shown and enabled, the only items with a hint, and never while focus is in a text field, select or contenteditable or a dialog is open (`menuKeysBlocked()`): the menu stays open when focus moves on by keyboard. Escape with focus inside an open panel closes it, the Columns panel through its discard confirm; the panel consumes that key, since the confirm it opens would otherwise receive the same Escape and close at once.
- **Side panels**, one at a time (`panel` in `TableViewer.tsx`, not in the URL): Columns beside the grid, History a drawer fixed over the right edge. Leaving the Columns panel for History goes through its discard confirm (`requestClose()` on its ref handle); closing either returns focus to the title button.
- **Footer.** `tableLastWriter()` in `TableFooter.tsx` derives "Last written by" from `last_write_source`, which the API sends to the owner only.

## Schema Editor

`TableSchemaEditor.tsx` edits a draft (`SchemaDraft` in `utils/tableSchemaOps.ts`) that keeps each column's key and each option's loaded spelling, so a rename stays a rename, and a save sends one `PUT /tables/{id}/schema` with `expected_schema_version`. `deriveSchemaChange()` turns the draft into operations; its header comment gives the order and the reason for each step. The order matters because the server applies the list to a working copy and addresses every column and option by its name at that point, so the client simulates the same copy: drops first to free names, renames resolved through chains and cycles, per-column settings before options, adds with `after`, and a reorder only when the result differs. The server has no operation that moves an existing option, so the editor never moves one and appends new ones.

`validateDraft()` mirrors the server's cheap rules ([Quest Tables -- Schema Operations](quest-tables.md#schema-operations)): names, options, defaults, the fixed type, single to multi only, a default for a required column added to a table with rows, the last column and option. A problem blocks Save, as does an empty change or one over `TABLE_SCHEMA_MAX_OPERATIONS`. A refusal carrying an `op_index` lands at its column, anything else in a banner.

A 409 `stale_schema`, or the detail's `schema_version` moving while the draft has edits, raises a banner: keep the edits re-based by key onto the newer schema (`rebaseDraft()` lists what it could not keep) or discard them. Without edits the draft re-bases silently. A 400 `rows_violate` shows the server's message, which names the offending row ids, and a link that filters the grid on the column, because the filter language cannot address `_id` (`violationLink()`); the link stays on this table, so the panel and its draft survive it.

Without `access.can_edit_schema` the panel is read-only, with `schema_deny_reason`. With edits, the panel's Close, Escape, Discard, a switch to History and a same-origin link click (`useUnsavedChangesGuard`) confirm first; back / forward and button navigation such as the Sidebar's rows are not intercepted and drop the draft. A save applies the returned detail through `useTable.applyDetail`, and the grid re-queries on the version change without waiting for `table_changed`.

`NewTableDialog.tsx` puts the same editor body (`SchemaEditorBody`) under a title, description and location: the user's tables or one of their projects, archived ones left out unless preselected. It sends `project_id` only for a project table and never a mode, since a project table takes its project's. `duplicate_title` lands at the title, a column spec error at its column (`detail.column`), anything else (`table_limit`, ...) in a banner; a created table opens in the viewer.

## History

`TableHistory.tsx` is for editors: every history route refuses anyone else, since before images can hold rows the owner deleted before sharing, so a 403, or a 404 `table_not_found`, from any call replaces the drawer with a lost-access state. `useTableChanges` pages the log newest first by `before_id`, one call in flight per table, and re-lists the loaded window on this table's `table_changed` after a quiet period that a burst cannot stretch past a cap (its header comment has the coalescing rules). A re-list replaces the window instead of patching it, because a restore flips `in_effect` on entries anywhere in it; an entry not in effect is struck through, with the reason as text.

A rows detail goes through `changeDetailToRowsDiff()`, which pairs the before and after images by `_id` into the card's `TableRowsDiff` shape, names columns from the detail's own `columns` (a column since dropped reads as removed, never as its key) and leaves out rows past the shorter of two cut images. A schema detail renders the card's schema diff, and change #1 the create card's column table. Details are cached per change under a key of the table id, its `schema_version` and the newest loaded restore entry, because row images are decoded with the current schema and `in_effect` moves with restores.

Restore (with `access.can_restore`) confirms with the number of data changes it rewinds: the entries on the newest entry's [replay path](quest-tables.md#restore) that are not on the target's, restore entries not counted, and "at least" when the paths leave the loaded pages (`restoreImpact()`); the confirm also says how to undo it. The button is disabled when the table is already in that state. The new restore entry goes on top at once, selected; the viewer applies `res.table`, and since a restore always bumps `schema_version` the grid re-queries.

## Card Previews

`ActionRequestPreviewFields.tsx` renders the field types `table_columns`, `table_schema_diff` and `table_rows_diff` with `TableColumnsPreview`, `TableSchemaDiffPreview` and `TableRowsDiffPreview`, stacked full width; a field whose payload key is missing falls back to its plain value. The schema diff and the row grid are the components History uses, so a change reads the same on the card that proposed it and in the log (History maps its row images onto the card's shape first). No preview shows a column key. The row grid is the `rows` variant of `SpreadsheetDiffPreview` (row labels and statuses, NULL cells distinct from empty ones), the grid of the spreadsheet card. Status colours are the `--diff-*` tokens in `index.css`, set for both schemes. Column types read the same in the Columns panel, the card column table, the schema diff and History through `columnTypeLabel()` (`utils/tableCells.tsx`): the editor's names, never the raw type names.

## Phone Layouts

Below `MOBILE_BREAKPOINT_PX` (`hooks/useIsMobile.ts`) the views render inside `MobileShell`, and no table surface is wider than the screen: the viewer header stacks the title over the chips (DocHeader's phone rules), the filter bar, notes, pager and footer wrap, and the grid keeps its own two-way scroll. The Columns panel is a full-screen sheet with its footer pinned, and the History drawer covers the screen, showing the list alone and an entry's detail full width with a control back to the list, as DocHistory does (a `useIsMobile` branch in `TableHistory.tsx`; Escape steps back). The New Table dialog fills the screen with its header and action row pinned. The CSS-only parts use the same 768px breakpoint.

## Realtime Consumers

`useTables` and `useProjectTablesIndex` re-fetch silently on `table_list_changed` behind a trailing debounce (`TABLES_REFRESH_DEBOUNCE_MS`, the fan-out's `TABLES_INDEX_REFRESH_DEBOUNCE_MS` the longer one), so a burst of writes to a table shared with everyone costs one re-fetch per list. `useTable` ignores that broadcast and follows `table_changed` for its own table only: it re-fetches the detail unless it already shows the event's `updated_at` and `schema_version`, which a null never matches, so a delete or revoked share reaches the viewer as its not-found state. An event arriving while a fetch is in flight runs one more fetch when it lands instead of superseding it, which under a burst of writes would drop every response.

A `table_changed` with an `updated_at` also re-queries the grid page, since a row write moves `updated_at` but the detail does not carry rows. An event whose `schema_version` differs from the loaded schema waits for the detail re-fetch instead, because old column names would 400 and the rows would be keyed by columns the loaded schema lacks; a rows page reporting a newer `schema_version` than the detail asks `useTable` to re-fetch. `useTableRows` coalesces refreshes the same way and keeps the last page on screen during a refetch, so a burst of agent writes cannot starve the grid.

`useTableChanges` follows `table_changed` for its table too ([History](#history)). The Columns panel follows the detail's `schema_version`, not the event, so it re-bases or raises its conflict banner only once `useTable` has the newer schema.

## Design Decisions

**Why one `PUT /schema` per save instead of a request per edit?** A save is one change in the log, so one restore point, and the server checks the whole batch against the rows at once; requests per edit would leave a half-applied schema when a later edit is refused.

**Why Move up / Move down buttons instead of drag reorder?** They work from the keyboard and with screen readers (focus stays on the moved card and a live region announces the new position) and need no drag-and-drop dependency.

**Why is the phone Columns sheet positioned against `.mobile-shell` instead of fixed?** `MobileShell` sizes the shell to the visual viewport, so a sheet inside it keeps its Save footer above the on-screen keyboard; a fixed sheet follows the layout viewport, which the keyboard covers on iOS. ModelSelector's phone sheet sits there for the same reason.
