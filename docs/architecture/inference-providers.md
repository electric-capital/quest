# Inference Providers (Admin Settings)

## Overview

Admin-only Settings > Inference Providers panel for LLM backend configuration. It manages two kinds of provider configuration:

- **Vertex AI** (exactly one). Credentials are display-only -- the panel shows what was detected from the environment (a `GOOGLE_APPLICATION_CREDENTIALS` service-account key or the gcloud ADC file) plus the effective `vertex_project_id`/`vertex_region` per model family and which layer each value came from (env var, `server_config.json`, or the gemini_vertex → anthropic project fallback). Its model catalog is the fixed `MODEL_REGISTRY` (`chat/llm/config.py`, Gemini + Claude); the one piece of admin state is which of those models are **enabled** (checkbox per model, stored as a disabled set). A disabled model is hidden from the picker and never health-checked; existing conversations keep running on it.

- **Provider instances** (zero or more): each is one configuration of a provider kind (`INSTANCE_KINDS` in `config/inference_providers.py` is the registry) with an admin-chosen label and its own admin-chosen model list. Eight kinds exist:
  - `anthropic` ("Anthropic") -- Anthropic's own API: the only credential is a **Claude API key** from console.anthropic.com (`sk-ant-...`, sent as `x-api-key`), requests go to `https://api.anthropic.com` through `AnthropicApiProvider`, a per-instance subclass of the Vertex `AnthropicProvider` (see [LLM Providers -- AnthropicProvider](llm-providers.md#anthropicprovider)) -- same sessions, streaming, prompt caching, thinking and attachments, no Vertex region and no refusal-fallback chain. Wire ids are the API's model ids: aliases such as `claude-sonnet-5` or dated snapshots such as `claude-haiku-4-5-20251001`. Models are added from a typeahead over the key-fetched `GET /v1/models` list (see [Anthropic catalog cache](inference-catalogs.md#anthropic-openai-and-gemini-catalog-caches)) or typed in; each row borrows the limits, thinking levels and list price of the Vertex registry entry serving the same model, so an `anthropic:` row prices like its Vertex twin.
  - `openai` ("OpenAI") -- OpenAI's own API: the only credential is an **OpenAI API key** (`sk-...`, bearer token), requests go to `https://api.openai.com/v1` through the shared `OpenRouterProvider` with OpenAI's request shape (`max_completion_tokens` instead of `max_tokens`, a picked thinking level as the top-level `reasoning_effort`, a few-token health check). Wire ids are OpenAI model ids (`gpt-5`, `gpt-4.1-mini`, `o4-mini`, dated snapshots). Models are added from a typeahead over the key-fetched `GET /v1/models` list reduced to chat models (see [OpenAI catalog cache](inference-catalogs.md#anthropic-openai-and-gemini-catalog-caches)); limits, prices and reasoning levels come from the hand-maintained `KNOWN_MODELS` table in `chat/llm/openai_catalog.py`, other chat models get defaults and no price.
  - `gemini` ("Google Gemini") -- the Gemini Developer API: the only credential is a **Gemini API key** from Google AI Studio (`AIza...`, sent as `x-goog-api-key`), requests go to `generativelanguage.googleapis.com` through `GeminiApiProvider`, a per-instance subclass of the Vertex `GeminiProvider` over `genai.Client(api_key=...)`. Wire ids are the API's model names without the `models/` prefix (`gemini-3.8-flash`). Models are added from a typeahead over the key-fetched `GET /v1beta/models` list (see [Gemini catalog cache](inference-catalogs.md#anthropic-openai-and-gemini-catalog-caches)), which publishes real token limits; prices and thinking levels come from the matching Vertex registry entry. A Vertex Gemini model and its Developer API twin are distinct model ids, so a conversation never mixes the two backends (thought signatures are not portable across them).
  - `openrouter` -- an OpenRouter configuration with its own API key, powering the `OpenRouterProvider` (see [LLM Providers -- OpenRouterProvider](llm-providers.md#openrouterprovider)). Models are added from a typeahead over the OpenRouter catalog (or typed in as a custom id).
  - `fireworks` ("Fireworks AI") -- a direct [Fireworks AI](https://fireworks.ai) configuration: the only credential is a **Fireworks API key** (created in the Fireworks dashboard under Settings > API keys, or with `firectl api-key create`; sent as `Authorization: Bearer <key>`), requests go to the kind's fixed `upstream_url` `https://api.fireworks.ai/inference/v1` (OpenAI-compatible chat completions, same `OpenRouterProvider` without the OpenRouter-only extras -- Fireworks includes usage in the final streamed chunk by itself). Wire ids are Fireworks resource names: `accounts/fireworks/models/<name>` for the shared serverless models, `accounts/<account>/deployments/<id>` for a dedicated deployment. Models are added from a typeahead over the Fireworks serverless catalog, which -- unlike OpenRouter's -- can only be read with a key, so it is fetched with the instance's own stored key once the key is saved (see [Fireworks catalog cache](inference-catalogs.md#fireworks-catalog-cache)); a deployment id is typed in as a custom id.
  - `nearai` ("NEAR AI") -- a direct [NEAR AI Cloud](https://cloud.near.ai) configuration: the only credential is a **NEAR AI API key** (created in the NEAR AI Cloud dashboard under an organization's workspace API keys; sent as `Authorization: Bearer <key>`), requests go to the kind's fixed `upstream_url` `https://cloud-api.near.ai/v1` (OpenAI-compatible chat completions, same `OpenRouterProvider` without the OpenRouter-only extras -- NEAR AI includes usage in the final streamed chunk, with the `prompt_tokens_details.cached_tokens` split of its automatic prompt cache); every request additionally carries the `x-no-aliasing: true` default header so the gateway never substitutes a different model for the one requested. Wire ids are `<vendor>/<model>` slugs like OpenRouter's (`deepseek/deepseek-v3.2`, `anthropic/claude-sonnet-5`); the same slug on an OpenRouter instance is a different qualified id. Models are added from a typeahead over NEAR AI's **public, priced** model list (no key needed, so the typeahead works before the key is saved; see [NEAR AI catalog cache](inference-catalogs.md#near-ai-catalog-cache)) or typed in as a custom id. Each catalog-added model is snapshotted with a `tee` label -- `enclave` for a model NEAR AI serves on its own hardware-attested TEE fleet, `proxy` for one it relays to a third-party provider -- shown as an informational Enclave / Proxy badge on the model row (nothing is enforced and no attestation is verified). The NEAR AI health check is a lookup in that catalog instead of a billed completion (see [Model health](#model-health-checks-server-global)).
  - `trustedrouter` ("TrustedRouter") -- a direct [TrustedRouter](https://trustedrouter.com) configuration: the only credential is a **TrustedRouter API key** (`sk-tr-v1-...`, sent as `Authorization: Bearer <key>`), requests go to the kind's fixed `upstream_url` `https://api.trustedrouter.com/v1` (OpenAI-compatible chat completions, same `OpenRouterProvider` without the OpenRouter-only extras). The gateway runs attested in Google Confidential Space (verifiable at https://trustedrouter.com/trust). Wire ids are `<vendor>/<model>` slugs like OpenRouter's (`deepseek/deepseek-v4-flash-0731`) plus TrustedRouter's own routes (`trustedrouter/auto`). Models are added from a typeahead over TrustedRouter's **public, priced** model list (no key needed; see [TrustedRouter catalog cache](inference-catalogs.md#trustedrouter-catalog-cache)) or typed in as a custom id.
  - `local` ("Self-hosted") -- an inference server the admin runs, identified by a **server URL** (`base_url`) and an **API type** (`api_type`): `openai` for the OpenAI-compatible chat-completions protocol every local server speaks (llama.cpp `llama-server`, vLLM, LM Studio, LocalAI, SGLang, text-generation-webui, Ollama's `/v1` shim…) or `ollama` for Ollama's native API (see [LLM Providers -- OllamaProvider](llm-providers.md#ollamaprovider) for why the native API is preferred for Ollama). The API key is optional (sent as a bearer token when set, e.g. for `llama-server --api-key` or a reverse proxy). Models are added from a typeahead over what the server reports right now (see [Self-hosted model discovery](inference-catalogs.md#self-hosted-model-discovery)) or typed in, and each row gets inline **name** and **context window** fields because local servers publish no friendly names.

  The `anthropic` and `gemini` kinds run on the vendors' own LLMProvider families (`llm_calls_anthropic` / `llm_calls_gemini` analytics tables, backend labels `anthropic` / `gemini`; the Vertex rows of the same tables carry `vertex`). Every other kind runs on the same `"openrouter"` LLMProvider family (OpenAI message format, history shape, `llm_calls_openrouter` analytics table); the kind's `backend` label (`openai` / `openrouter` / `fireworks` / `nearai` / `trustedrouter` / `local`) tells their rows apart. Each registry entry also names its fixed `upstream_url` (null for the endpoint-carrying `local` kind) and its `catalog` source for the "Add model" typeahead (`openrouter` = the shared public list, `anthropic` / `openai` / `gemini` / `fireworks` = the instance's key-fetched vendor catalog, `nearai` = NEAR AI's public list, `trustedrouter` = TrustedRouter's public list, `server` = live discovery; `chat/llm/model_setup.py` `fetch_instance_catalog()` dispatches on it for every admin path). Several instances of a kind can coexist (a personal and a team OpenRouter key with different curated models; a llama.cpp box and an Ollama box); the "+ Add ... configuration" buttons at the bottom of the section create one, in `INSTANCE_KINDS` order (the direct vendor kinds first). Every instance model carries the same enable checkbox.

  **First-run quick setup.** While `GET /app/api/config` reports no available model, an admin's composer is replaced by the model setup card (`frontend/src/components/ModelSetupCard.tsx`, see [Frontend -- Composer](frontend.md#composer-component)): pick a kind, paste its key (or a self-hosted server's URL and API type), Connect. `POST /admin/inference-providers/quick-setup` stores the credential on a new instance of the kind (or reuses one of that kind that serves no available model yet, so a corrected key never piles up empty instances), fetches the catalog fresh with it and adds the kind's **suggested models** (`suggested_models()` in `chat/llm/model_setup.py`: the models Quest has real metadata for -- the registry-matched Claude / Gemini models and the known OpenAI families, the curated legacy ids for the OpenRouter-shaped routers, the statically priced serverless models for Fireworks, every model a self-hosted server reports). The first suggestion is added alone and health-checked live; only when it passes are the rest added (rechecked in the background), so a rejected key leaves the instance connected but model-less. Unlike models added from Settings, quick-setup models are **not** written to Model Selection with `allow_private` off -- the admin is connecting the deployment's first model for private conversations, and the card says so. A kind with nothing to suggest leaves the key saved and the card sends the admin to Settings > Inference Providers to pick models.

How the enabled models are then *presented* to users -- which ones sit at the top level of the composer's model menu with what descriptor, and whether each may be used in private or public-project conversations -- is a separate admin section, Settings > Model Selection (see [Model Selection](model-selection.md)); this panel only decides which models exist and are enabled. One hand-off between the two: a model added to an instance here is recorded in Model Selection as **not allowed in private conversations** (public-project use stays open) the moment it is added, so a provider configured for public projects never receives private conversations' data by default; the note under each instance's model list links to Model Selection, where the admin allows it deliberately.

Every model row shows the **real model id string used in API calls** (the Vertex publisher id such as `claude-haiku-4-5`, the Claude API alias such as `claude-sonnet-5`, the OpenAI id such as `gpt-5`, the OpenRouter wire id such as `deepseek/deepseek-v4-flash-0731`, the Fireworks resource name such as `accounts/fireworks/models/deepseek-v3p1`, the NEAR AI slug such as `deepseek/deepseek-v3.2`, or the self-hosted server's model name such as `qwen2.5:0.5b` / the llama.cpp `--alias`) as its primary label, the friendly name muted beside it, and a liveness dot for the stored health verdict.

### Qualified model ids

Models served by an instance are identified everywhere -- `conversations.model`, `routines.model`, the per-user `default_model` / `slack_default_model` settings, the health store, `llm_calls_openrouter.model` -- by `<instance_id>:<wire_id>`, e.g. `openrouter:deepseek/deepseek-v4-flash-0731`, `fireworks:accounts/fireworks/models/deepseek-v3p1`, `nearai:deepseek/deepseek-v3.2` or `local:qwen2.5:0.5b`. Instance ids match `INSTANCE_ID_RE` (`[a-z0-9-]`, no `:` or `/`) and `split_model_id()` splits on the FIRST colon whose left part is a valid instance id, so a wire id's own colons (Ollama tags, OpenRouter `:variant` suffixes) stay inside the wire id; every OpenRouter wire id contains a `/`, which is what keeps the bare legacy-id fallback unambiguous. Vertex ids stay bare. The single pre-instances OpenRouter configuration is instance `openrouter` (its credential file was already `openrouter.json`); alembic migration `b8e4d2a7c1f5` prefixed the bare ids stored before instances existed, and `resolve_model()` still maps a bare OpenRouter id onto that instance as a fallback. See [LLM Providers -- Model resolution](llm-providers.md#model-resolution).

### Storage

Non-secret configuration lives in `DATA_DIR / "inference_providers.json"` (`load_inference_config()` / `save_inference_config()`, normalized on read and write, atomic writes like `feature_gates.json`):

```json
{
  "version": 1,
  "vertex": {"disabled_models": ["claude-opus-4-6"]},
  "instances": [
    {"id": "openrouter", "kind": "openrouter", "label": "OpenRouter",
     "models": [{"id": "deepseek/deepseek-v4-flash-0731", "enabled": true,
                 "name": "DeepSeek: DeepSeek V4 Flash", "context_length": 1310720,
                 "max_completion_tokens": 384000,
                 "pricing": {"prompt": 0.15, "completion": 0.6, "cache_read": 0.003}}]},
    {"id": "fireworks", "kind": "fireworks", "label": "Fireworks AI",
     "models": [{"id": "accounts/fireworks/models/deepseek-v3p1", "enabled": true,
                 "name": "DeepSeek V3.1", "context_length": 163840,
                 "max_completion_tokens": null,
                 "pricing": {"prompt": 0.56, "completion": 1.68, "cache_read": 0.056}}]},
    {"id": "nearai", "kind": "nearai", "label": "NEAR AI",
     "models": [{"id": "deepseek/deepseek-v3.2", "enabled": true,
                 "name": "deepseek-v3.2", "context_length": 128000,
                 "max_completion_tokens": null,
                 "pricing": {"prompt": 1.1, "completion": 1.1, "cache_read": 0.55}}]},
    {"id": "local", "kind": "local", "label": "Ollama box",
     "base_url": "http://192.168.1.20:11434", "api_type": "ollama",
     "models": [{"id": "qwen2.5:0.5b", "enabled": true, "name": "Qwen2.5 0.5b",
                 "context_length": 32768, "max_completion_tokens": null,
                 "pricing": {"prompt": 0.0, "completion": 0.0}}]}
  ]
}
```

`base_url` / `api_type` exist only on `local` instances (`normalize_base_url()` accepts `http(s)://` origins with an optional path prefix, adds `http://` to a bare `host:port`, and strips trailing slashes and a trailing `/v1`; an unknown `api_type` falls back to `openai`). `instance_configured()` is the per-kind readiness check: a stored key for OpenRouter, Fireworks and NEAR AI, a base URL for self-hosted (`get_configured_models()` uses it, so a self-hosted instance needs no key at all).

Per-model `name` / `context_length` / `max_completion_tokens` / `pricing` ($ per 1M tokens) -- and, for the router kinds, the catalog row's `reasoning` object, which decides the thinking levels the composer offers for the model (see [LLM Providers -- Thinking effort](llm-providers.md#thinking-effort)) -- are a **snapshot** taken when the model is added -- from the OpenRouter catalog, the Fireworks catalog, the NEAR AI catalog, or from the self-hosted server's own answer -- so nothing at request time depends on any of them: the limits feed the `ModelSpec` (output capped at `MAX_INSTANCE_OUTPUT_TOKENS`), the pricing feeds `db/llm_pricing.py`. Only `pricing` is re-read from the cached catalog on every save of the model list; a changed price moves the old snapshot into the model's `pricing_history` with an `until` stamp, and `instance_model_pricing(wire_id, at)` returns the snapshot in force at a call's time, so cost reports never reprice earlier calls (looked up by wire id with the static `_OPENROUTER_PRICING` table as the fallback for models no instance lists any more and the static `_FIREWORKS_PRICING` table for Fireworks wire ids, which never have snapshot pricing). A custom id the catalog does not list (an OpenRouter or NEAR AI id missing from the list, a Fireworks dedicated deployment) gets `name = id`, `DEFAULT_INSTANCE_CONTEXT_LENGTH` / `DEFAULT_INSTANCE_MAX_OUTPUT_TOKENS` and no pricing ("no estimate" in dashboards); Fireworks publishes neither prices nor a per-model output cap through its API, so its catalog models always have `pricing: null` and keep the default output limit; their rows are costed from `_FIREWORKS_PRICING` in `db/llm_pricing.py`, a hand-maintained mirror of the public serverless price list keyed by wire id (like the Vertex tables; ids the list lacks -- the `auto` meta-routers, dedicated deployments -- show "no estimate"). Self-hosted models always get the explicit zero `LOCAL_MODEL_PRICING` (free per token), and the admin can overwrite `name` and `context_length` per model from the card; for an Ollama instance `context_length` is also the `num_ctx` requested on every call.

API keys live in one file per instance under `DATA_DIR / "inference_credentials" / "<instance_id>.json"` (0600/0700, atomic writes, encrypted at rest in the same `{"encrypted": ...}` wrapper as the service-credential store with `encrypt_plaintext_inference_files()` sweeping pre-baked plaintext files -- see [Encryption at Rest](encryption-at-rest.md)). The instance id IS the credential file stem: `load_inference_config()` synthesizes (and persists) an instance entry for every credential file that has none, of the kind named by the stem (`kind_for_credential_file()`: a key-holding kind name with an optional `-<n>` suffix, so `fireworks.json` / `fireworks-2.json` become Fireworks instances and `nearai.json` a NEAR AI one; the legacy `openrouter.json` becomes the `openrouter` instance seeded with the historical curated models (`_LEGACY_OPENROUTER_MODELS`), any other stem an OpenRouter instance). A credential file may carry an optional `models` list beside `api_key` (wire ids or full `{id, name, context_length, ...}` entries, normalized like any model entry) that seeds the synthesized instance's model list -- consulted only while the instance has no config entry -- which is how the local-mode dev-config `inference_credentials` pre-baking produces a ready-to-use instance (see [Run Modes](run-modes.md)); without it the list starts empty for the admin to fill. Deleting an instance deletes its credential file too, otherwise the next load would resurrect it.

Because `get_available_models()` re-reads the config, the credential store and the health store on every call, every save takes effect without a restart.

### Model catalogs

Where each kind's "Add model" typeahead and metadata snapshots come from -- the cached OpenRouter, Fireworks, NEAR AI, TrustedRouter and direct-vendor catalogs and live self-hosted discovery -- is in [Inference Provider Catalogs](inference-catalogs.md).

## Model Health Checks (server-global)

Per-model health is **server state**, not a per-request UI probe. `ModelHealthStore` (`chat/llm/health.py`) keeps the latest verdict per (qualified) model id -- `{ok, error, checked_at}` -- in memory, mirrored atomically to `data/model_health.json` (`MODEL_HEALTH_FILE` in `config/paths.py`) so it survives restarts. At startup the quest lifespan launches `run_startup_model_checks()` as a background task: it checks every model returned by `get_configured_models()` -- enabled, credentialed, non-deprecated; so **disabled models are never checked** and an unconfigured deployment runs zero checks -- with concurrency bounded to 4 to avoid tripping per-project rate limits, then logs a summary.

The store **drives the model picker**: `get_available_models()` (what `GET /app/api/config` returns as `available_models`) is `get_configured_models()` minus every model whose latest verdict is an explicit failure. A never-checked model stays visible -- only a recorded failing check hides one, so a fresh boot or a deleted `model_health.json` can never empty the picker -- and health only filters *selection*: existing conversations and routines on an unhealthy model keep running.

Recovery paths are the startup sweep (which deliberately iterates the health-blind configured list so hidden models keep being rechecked), the admin per-model Recheck, and the automatic background recheck (`schedule_model_rechecks()`) after an instance key/model-list save or a Vertex model being re-enabled. Verdicts of models removed from an instance (or of a deleted instance) are dropped via `ModelHealthStore.forget()`.

A check is a **minimal live inference call** through the real provider instances (`check_model_access()` on each provider: 1 output token for Claude, OpenRouter, Fireworks, TrustedRouter and self-hosted servers, 16 completion tokens on an OpenAI instance (its reasoning models need room to answer and reject `max_tokens`) -- on Ollama a non-streaming `/api/chat` call that also loads the model, so an out-of-memory model fails here -- a ~25-token cap for Gemini) -- deliberately not a metadata lookup, so it surfaces exactly what a real send would hit: a Claude model never enabled in Vertex Model Garden, bad key, wrong project/region, quota exhaustion. The one exception is **NEAR AI**: `check_model_access()` on a `nearai` instance resolves the endpoint (so a missing key is still reported) and then looks the model up in the cached public catalog (`_check_nearai_catalog()`): not listed → failing with "not in NEAR AI's catalog", listed without `tools` in a known capability list → failing (Quest's agent loop needs tool calling; a `null` list claims nothing and passes), catalog unreachable with no cache → failing with the fetch error. The startup sweep checks every configured model on every boot and NEAR AI documents no rate limits, so a billed completion per model per restart bought little -- a bad key shows up on the first real turn with NEAR AI's own auth error instead. `check_model()` resolves the id with `resolve_model()` (so the right instance's provider object and key are used), wraps the call with a 45s timeout and returns failures as data with a compact extracted error (`extract_error_message()` understands both the anthropic `body.error.message` shape and google-genai's `code`/`message` attributes, truncated to 600 chars).

## Admin API

All endpoints are admin-gated (403 otherwise, incl. while impersonating) and live in `chat/routes/admin.py`:

- **GET `/admin/inference-providers`** → `{vertex, instances, kinds, api_types}`. `vertex` is the detected environment (`detail`) plus its model rows; each `instances[]` entry is `{id, kind, kind_label, label, configured, source, credentials: {api_key_set}, hint, key_required, base_url, api_type, models}` (never the key; `base_url` / `api_type` are null on OpenRouter, Fireworks and NEAR AI instances, `key_required` is false on self-hosted ones, `configured` follows `instance_configured()`). Model rows are `{id, wire_id, display_name, family, enabled, max_input_tokens, discontinued_on, status}` with `id` the stored/qualified id, `discontinued_on` the registry's announced provider shutdown date (Vertex only, else null; the row disappears on that date) and `status` the stored verdict or null. `kinds` lists the addable instance kinds in `INSTANCE_KINDS` order (`{kind, label, endpoint, catalog, hint, key_required}` -- `catalog` one of `anthropic` / `openai` / `gemini` / `openrouter` / `fireworks` / `nearai` / `trustedrouter` / `server`, telling the card which typeahead source to use; `hint` / `key_required` feed the first-run setup card), `api_types` the self-hosted API types (`{id, label, description}`).
- **PUT `/admin/inference-providers/vertex`** `{disabled_models}` -- full replacement of the Vertex disabled set (non-registry ids → 400 `unknown_model`); newly re-enabled configured models are rechecked in the background.
- **POST `/admin/inference-providers/instances`** `{kind, label?}` -- adds an empty instance with a server-generated id (`anthropic`, `anthropic-2`, ..., `openai`, ..., `gemini`, ..., `openrouter`, `openrouter-2`, ..., `fireworks`, `fireworks-2`, ..., `nearai`, `nearai-2`, ..., `local`, `local-2`, ...; orphaned credential files count as taken); unknown kinds → 400 `unknown_kind`.
- **PUT `/admin/inference-providers/instances/{id}`** `{label?, api_key?, base_url?, api_type?, models?}` -- omitted = keep; empty `api_key` keeps the stored key (400 `invalid_params` when a key-required kind has nothing to keep and nothing else to save; on self-hosted instances an empty key is simply "no key"); `base_url` / `api_type` are accepted on self-hosted instances only (400 on the fixed-upstream kinds; malformed URL or unknown type → 400 `invalid_params`); `models` is a full-replacement `[{id, enabled, name?, context_length?}]` list of wire ids in display order, new entries snapshotted from the kind's catalog -- the cached OpenRouter catalog, the cached vendor catalog fetched with the instance's key (Anthropic, OpenAI, Gemini, Fireworks), the cached public NEAR AI / TrustedRouter catalog, or the self-hosted server's live model list (`_catalog_snapshots()` over `fetch_instance_catalog()`) -- the optional `name` / `context_length` (positive) overriding the stored snapshot, removed entries' health verdicts dropped, and entries new to the instance written to Model Selection with `allow_private` off via `restrict_new_models()` (existing selection entries kept; see [Model Selection](model-selection.md)). A key or endpoint change drops cached SDK clients (an endpoint change also the cached provider object, since the API type selects the provider class); any of these changes schedules rechecks of the instance's configured models.
- **DELETE `/admin/inference-providers/instances/{id}`** -- removes the config entry, the credential file, the cached provider object and the models' verdicts. Conversations referencing its models keep their ids and fail at their next send with a clear not-configured error, like after a revoked key.
- **GET `/admin/inference-providers/openrouter/catalog?q=&limit=&refresh=`** -- typeahead candidates `{models, fetched_at, stale, error}` from the shared OpenRouter catalog.
- **GET `/admin/inference-providers/instances/{id}/catalog?q=&limit=&refresh=`** -- an instance's OWN catalog, `{models, error}`: for a self-hosted instance the models its server reports right now (live, uncached; `error` set with an empty list when the server is unreachable or no URL is saved yet; `refresh` ignored), for a Fireworks, Anthropic, OpenAI or Gemini instance the cached vendor catalog fetched with the instance's stored key (`refresh=true` re-fetches; no key saved yet → `{"models": [], "error": "No API key saved yet."}` without a fetch; a rejected key → the stale cache or an empty list with the HTTP error), for a NEAR AI instance the cached public NEAR AI catalog (`refresh=true` re-fetches; served whether or not a key is saved, a failed fetch → the stale cache or an empty list with the error; every row carries its `tee` label); 400 on OpenRouter instances, whose typeahead is the shared route above.
- **POST `/admin/inference-providers/test-model`** `{model}` → `{model, ok, error, checked_at}` -- live recheck that updates the store (unknown → 404, disabled → 400 `model_disabled`; a bare legacy OpenRouter id is recorded under its qualified id).
- **POST `/admin/inference-providers/quick-setup`** `{kind, api_key?, base_url?, api_type?}` → `{instance, added, check, catalog_error}` -- the first-run setup card's one-step connect described in the Overview: unknown kind → 400 `unknown_kind`; a key-holding kind without a key, or the self-hosted kind without a valid URL / with an unknown API type → 400 `invalid_params`. `instance` is the card payload of the (new or reused) instance, `added` the qualified ids added, `check` the first suggestion's live verdict (null when the kind had nothing to suggest) and `catalog_error` the catalog fetch error (a rejected key on a key-fetched catalog shows up here with nothing added).

## Frontend

## Adding a Provider Kind

A kind is an `INSTANCE_KINDS` entry naming its LLMProvider implementation, analytics backend label, key requirement, whether it carries its own endpoint (else its fixed `upstream_url`) and its `catalog` source, plus a `get_provider_instance()` branch constructing that provider with the instance id. The stores, the admin endpoints, the settings cards and the add-button footer are all driven by the registry; the `local` kind is the worked example of an endpoint-carrying kind (extra instance fields normalized in `_normalize_instance()`, accepted by the PUT body, rendered by `InstanceCard` when the kind's `endpoint` flag is set), `fireworks` and `openai` the worked examples of a fixed-upstream, key-required kind with its own key-fetched catalog module (the newer `openai` one on the shared `chat/llm/catalog_cache.py` plumbing), `nearai` the smallest one (a fixed upstream whose public catalog already has the OpenRouter row shape, so its module is a filter over `normalize_openrouter_entry()`), and `anthropic` / `gemini` the examples of a kind on a non-OpenAI provider family (a per-instance subclass of the Vertex provider that only swaps the client, selected by `get_provider_instance()` when an instance id is passed) -- any other OpenAI-compatible hosted API (Together, Groq, ...) follows the same recipe: a registry entry with the upstream URL, a catalog module producing the shared row shape (or `catalog: "openrouter"`-style reuse of an existing one), a branch in `catalog_module()` / `fetch_instance_catalog()` (chat/llm/model_setup.py), and a `suggested_models()` rule if the quick setup should pick models for it.

## Design Decisions

**Why qualified model ids instead of a separate instance column?**
The model id is already the universal key -- conversation and routine rows, per-user defaults, the health store, analytics rows, the frontend catalog -- so folding the instance into it keeps every one of those paths unchanged and the migration a pure string prefix. A separate column would have had to be threaded through the WebSocket send path, the scheduler, sub-agent spawning and analytics.

**Why snapshot catalog metadata instead of reading the catalog at request time?**
Sends must not depend on openrouter.ai being reachable, and pricing must stay stable for the rows already recorded. The snapshot is refreshed only when the admin adds the model again. Since the provider captures the amount OpenRouter actually charged per call (`llm_calls_openrouter.cost`, see [LLM Providers](llm-providers.md#openrouterprovider)), the snapshot only prices rows recorded before that capture existed -- drift in it no longer skews the reports.

**Why do self-hosted servers, Fireworks and NEAR AI reuse the `openrouter` provider family instead of getting their own?**
Every local server, Fireworks and NEAR AI speak the OpenAI chat-completions protocol, and the provider name is woven through the history envelope (`sdk_history.json`), the interruption-marker writer, the analytics table choice and the frontend usage cell. A separate `local`, `fireworks` or `nearai` provider would have duplicated all of that for an identical message format. The kind's `backend` label (`local` / `fireworks` / `nearai`) is what distinguishes the rows in cost reports; the instance label is folded into the model's display name in pickers ("Qwen2.5 0.5b (Ollama box)"), so users still see where a model runs.

**Why a direct Fireworks kind when OpenRouter already routes to Fireworks?**
A direct key skips the OpenRouter markup and routing, keeps traffic inside one vendor agreement (data-handling terms, invoicing) and reaches dedicated deployments (`accounts/<account>/deployments/<id>`), which OpenRouter cannot address. Fireworks' catalog needs a key to read, which is why its typeahead is a per-instance route (fetched with the saved key) rather than the public OpenRouter one; one cache still serves every Fireworks instance because the public list is the same for every key. Cost visibility is what a direct key gives up: Fireworks reports no per-request cost (its usage object carries token counts only, and it 400s on OpenRouter's `usage: {"include": true}` opt-in; its billing API aggregates per day, never per request) and publishes no per-model prices through its API, so Fireworks rows are list-price estimates from the hand-maintained `_FIREWORKS_PRICING` table in `db/llm_pricing.py` -- a mirror of https://docs.fireworks.ai/serverless/pricing kept like the Vertex tables, to be updated by hand when Fireworks changes prices or adds models (the usage columns still count tokens, incl. the cached-prompt split Fireworks reports, which the estimate bills at the cached rate).

**Why a direct NEAR AI kind, and why is its catalog a per-instance route when it needs no key?**
NEAR AI Cloud sells the same `<vendor>/<model>` slugs as OpenRouter but on its own terms -- several models run in TEEs with attestation, billing is one vendor agreement, and the catalog publishes real per-token prices incl. cache reads, so its rows get cost estimates from the snapshot (Fireworks' come from the static table instead). The typeahead still goes through `GET /instances/{id}/catalog` rather than a second shared route because the card already picks its search by the kind's `catalog` source; the route simply skips the key check for this source, which is also why the combobox is enabled before the key is saved (`catalogNeedsConfig` covers only the server-fetched and key-fetched sources).

**Why a native Ollama transport rather than Ollama's OpenAI-compatible endpoint?**
The compatibility endpoint cannot set the context window: Ollama runs every model at a small default (its startup log on a GPU-less box says `default_num_ctx=4096`) and silently truncates the prompt, which for this app means the system prompt's tool instructions are the first thing to go. The native `/api/chat` takes `options.num_ctx` per request. The transport is a subclass that only swaps the wire format, so history, repair and analytics stay shared. Ollama's official workaround (a derived model with `PARAMETER num_ctx` in a Modelfile) would push a per-app concern onto every admin.

**Why is self-hosted pricing an explicit $0 instead of "unknown"?**
A null price makes every report that includes the model show no total at all (the "no estimate" rule protects against under-reporting an unpriced paid model). A self-hosted model has no per-token charge, so zero is the honest figure and keeps the deployment's other spend visible; the row is still tagged `estimated`, and an admin who wants to reflect hardware cost can leave the number at zero and read the token columns.

**Why is self-hosted model discovery not cached, while the OpenRouter, Fireworks and NEAR AI catalogs are?**
The OpenRouter, Fireworks and NEAR AI catalogs are hosted lists of dozens to hundreds of entries that change daily and cost a remote request; a local box's list changes whenever the admin loads or pulls a model and is a single fast LAN request. Caching it would only make the typeahead lie right after `ollama pull`.

**Why is the NEAR AI health check a catalog lookup when every other provider gets a live completion?**
The live call is the better check -- it hits exactly what a real send hits -- and it stays the rule. NEAR AI is the exception because the two costs are lopsided there: the startup sweep re-checks every configured model on every boot, a NEAR AI configuration tends to list many of its ~50 chat models, each check is a billed completion, and NEAR AI documents no rate limits that a flood of 1-token calls would need to respect. What the live call catches that the lookup does not -- a revoked or unfunded key -- surfaces on the first real turn with NEAR AI's own auth error, while the lookup still catches the common configuration mistakes (a typo'd or retired slug, a model listed without tool calling) and a missing key.

**Why is the Enclave / Proxy label only a badge?**
Nothing in Quest verifies an attestation: the label repeats what NEAR AI's public metadata list claims about where a model runs (`providerType` / `verifiable` / `attestationSupported`), folded fail-closed so only NEAR's unambiguous positive signal reads "Enclave". It is there so an admin choosing between two slugs can see which one NEAR AI serves from its own TEE fleet and which it relays to a third party; enforcing it (refusing proxy models, pinning conversations to attested models) would need real attestation verification and is not built.

**Why is Vertex read-only in the panel?**
Vertex auth is ambient (ADC/env), typically provisioned by `run.py`, the prod bootstrap, or deployment tooling, and consumed by Google SDKs outside the app's control; the panel's job is to make the detected state visible, not to own it. Metadata-server credentials (GCE instance service accounts) are intentionally not probed to keep the settings request free of network calls, and the card says so. Enabling/disabling individual Vertex models is app state, so that part is editable.

**Why a store separate from `service_credentials/`?**
Inference providers are not upstream data integrations: they have their own instance registry, a different form shape (bare API key vs OAuth client), and their own settings section. Sharing the directory would leak them into the Service Credentials list endpoint, which iterates `KNOWN_SERVICES`. The file format and atomic-write scheme are deliberately identical.

**Why is the API key write-only with empty-means-keep?**
Same reasoning as service credentials: the browser never needs the key back, and an empty save keeps the stored key -- see [Service Credentials](service-credentials.md).
