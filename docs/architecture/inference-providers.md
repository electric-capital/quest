# Inference Providers (Admin Settings)

## Overview

Admin-only Settings > Inference Providers panel for LLM backend configuration. It manages two kinds of provider configuration:

- **Vertex AI** (exactly one). Credentials are display-only -- the panel shows what was detected from the environment (a `GOOGLE_APPLICATION_CREDENTIALS` service-account key or the gcloud ADC file) plus the effective `vertex_project_id`/`vertex_region` per model family and which layer each value came from (env var, `server_config.json`, or the gemini_vertex → anthropic project fallback). Its model catalog is the fixed `MODEL_REGISTRY` (`chat/llm/config.py`, Gemini + Claude); the one piece of admin state is which of those models are **enabled** (checkbox per model, stored as a disabled set). A disabled model is hidden from the picker and never health-checked; existing conversations keep running on it.

- **Provider instances** (zero or more): each is one configuration of a provider kind (`INSTANCE_KINDS` in `config/inference_providers.py` is the registry) with an admin-chosen label and its own admin-chosen model list. Three kinds exist:
  - `openrouter` -- an OpenRouter configuration with its own API key, powering the `OpenRouterProvider` (see [LLM Providers -- OpenRouterProvider](llm-providers.md#openrouterprovider)). Models are added from a typeahead over the OpenRouter catalog (or typed in as a custom id).
  - `fireworks` ("Fireworks AI") -- a direct [Fireworks AI](https://fireworks.ai) configuration: the only credential is a **Fireworks API key** (created in the Fireworks dashboard under Settings > API keys, or with `firectl api-key create`; sent as `Authorization: Bearer <key>`), requests go to the kind's fixed `upstream_url` `https://api.fireworks.ai/inference/v1` (OpenAI-compatible chat completions, same `OpenRouterProvider` without the OpenRouter-only extras -- Fireworks includes usage in the final streamed chunk by itself). Wire ids are Fireworks resource names: `accounts/fireworks/models/<name>` for the shared serverless models, `accounts/<account>/deployments/<id>` for a dedicated deployment. Models are added from a typeahead over the Fireworks serverless catalog, which -- unlike OpenRouter's -- can only be read with a key, so it is fetched with the instance's own stored key once the key is saved (see [Fireworks catalog cache](#fireworks-catalog-cache)); a deployment id is typed in as a custom id.
  - `local` ("Self-hosted") -- an inference server the admin runs, identified by a **server URL** (`base_url`) and an **API type** (`api_type`): `openai` for the OpenAI-compatible chat-completions protocol every local server speaks (llama.cpp `llama-server`, vLLM, LM Studio, LocalAI, SGLang, text-generation-webui, Ollama's `/v1` shim…) or `ollama` for Ollama's native API (see [LLM Providers -- OllamaProvider](llm-providers.md#ollamaprovider) for why the native API is preferred for Ollama). The API key is optional (sent as a bearer token when set, e.g. for `llama-server --api-key` or a reverse proxy). Models are added from a typeahead over what the server reports right now (see [Self-hosted model discovery](#self-hosted-model-discovery)) or typed in, and each row gets inline **name** and **context window** fields because local servers publish no friendly names.

  All three kinds run on the same `"openrouter"` LLMProvider family (OpenAI message format, history shape, `llm_calls_openrouter` analytics table); the kind's `backend` label (`openrouter` / `fireworks` / `local`) tells their rows apart. Each registry entry also names its fixed `upstream_url` (null for the endpoint-carrying `local` kind) and its `catalog` source for the "Add model" typeahead (`openrouter` = the shared public list, `fireworks` = the instance's key-fetched catalog, `server` = live discovery). Several instances of a kind can coexist (a personal and a team OpenRouter key with different curated models; a llama.cpp box and an Ollama box); the "+ Add OpenRouter / Fireworks AI / Self-hosted configuration" buttons at the bottom of the section create one. Every instance model carries the same enable checkbox.

How the enabled models are then *presented* to users -- which ones sit at the top level of the composer's model menu with what descriptor, and whether each may be used in private or public-project conversations -- is a separate admin section, Settings > Model Selection (see [Model Selection](model-selection.md)); this panel only decides which models exist and are enabled.

Every model row shows the **real model id string used in API calls** (the Vertex publisher id such as `claude-haiku-4-5`, the OpenRouter wire id such as `deepseek/deepseek-v4-flash-0731`, the Fireworks resource name such as `accounts/fireworks/models/deepseek-v3p1`, or the self-hosted server's model name such as `qwen2.5:0.5b` / the llama.cpp `--alias`) as its primary label, the friendly name muted beside it, and a liveness dot for the stored health verdict.

### Qualified model ids

Models served by an instance are identified everywhere -- `conversations.model`, `routines.model`, the per-user `default_model` / `slack_default_model` settings, the health store, `llm_calls_openrouter.model` -- by `<instance_id>:<wire_id>`, e.g. `openrouter:deepseek/deepseek-v4-flash-0731`, `fireworks:accounts/fireworks/models/deepseek-v3p1` or `local:qwen2.5:0.5b`. Instance ids match `INSTANCE_ID_RE` (`[a-z0-9-]`, no `:` or `/`) and `split_model_id()` splits on the FIRST colon whose left part is a valid instance id, so a wire id's own colons (Ollama tags, OpenRouter `:variant` suffixes) stay inside the wire id; every OpenRouter wire id contains a `/`, which is what keeps the bare legacy-id fallback unambiguous. Vertex ids stay bare. The single pre-instances OpenRouter configuration is instance `openrouter` (its credential file was already `openrouter.json`); alembic migration `b8e4d2a7c1f5` prefixed the bare ids stored before instances existed, and `resolve_model()` still maps a bare OpenRouter id onto that instance as a fallback. See [LLM Providers -- Model resolution](llm-providers.md#model-resolution).

### Storage

Non-secret configuration lives in `DATA_DIR / "inference_providers.json"` (`load_inference_config()` / `save_inference_config()`, normalized on read and write, atomic writes like `feature_gates.json`):

```json
{
  "version": 1,
  "vertex": {"disabled_models": ["claude-opus-4-6"]},
  "instances": [
    {"id": "openrouter", "kind": "openrouter", "label": "OpenRouter",
     "models": [{"id": "deepseek/deepseek-v4-flash-0731", "enabled": true,
                 "name": "DeepSeek: DeepSeek V4 Flash", "context_length": 1310720,
                 "max_completion_tokens": 384000,
                 "pricing": {"prompt": 0.15, "completion": 0.6, "cache_read": 0.003}}]},
    {"id": "fireworks", "kind": "fireworks", "label": "Fireworks AI",
     "models": [{"id": "accounts/fireworks/models/deepseek-v3p1", "enabled": true,
                 "name": "DeepSeek V3.1", "context_length": 163840,
                 "max_completion_tokens": null,
                 "pricing": {"prompt": 0.56, "completion": 1.68, "cache_read": 0.056}}]},
    {"id": "local", "kind": "local", "label": "Ollama box",
     "base_url": "http://192.168.1.20:11434", "api_type": "ollama",
     "models": [{"id": "qwen2.5:0.5b", "enabled": true, "name": "Qwen2.5 0.5b",
                 "context_length": 32768, "max_completion_tokens": null,
                 "pricing": {"prompt": 0.0, "completion": 0.0}}]}
  ]
}
```

`base_url` / `api_type` exist only on `local` instances (`normalize_base_url()` accepts `http(s)://` origins with an optional path prefix, adds `http://` to a bare `host:port`, and strips trailing slashes and a trailing `/v1`; an unknown `api_type` falls back to `openai`). `instance_configured()` is the per-kind readiness check: a stored key for OpenRouter and Fireworks, a base URL for self-hosted (`get_configured_models()` uses it, so a self-hosted instance needs no key at all).

Per-model `name` / `context_length` / `max_completion_tokens` / `pricing` ($ per 1M tokens) are a **snapshot** taken when the model is added -- from the OpenRouter catalog, the Fireworks catalog, or from the self-hosted server's own answer -- so nothing at request time depends on any of them: the limits feed the `ModelSpec` (output capped at `MAX_INSTANCE_OUTPUT_TOKENS`), the pricing feeds `db/llm_pricing.py` (`instance_model_pricing()`, looked up by wire id with the static `_OPENROUTER_PRICING` table as the fallback for models no instance lists any more). A custom id the catalog does not list (an OpenRouter id missing from the list, a Fireworks dedicated deployment) gets `name = id`, `DEFAULT_INSTANCE_CONTEXT_LENGTH` / `DEFAULT_INSTANCE_MAX_OUTPUT_TOKENS` and no pricing ("no estimate" in dashboards); Fireworks publishes no per-model output cap, so its catalog models keep the default output limit. Self-hosted models always get the explicit zero `LOCAL_MODEL_PRICING` (free per token), and the admin can overwrite `name` and `context_length` per model from the card; for an Ollama instance `context_length` is also the `num_ctx` requested on every call.

API keys live in one file per instance under `DATA_DIR / "inference_credentials" / "<instance_id>.json"` (0600/0700, atomic writes, encrypted at rest in the same `{"encrypted": ...}` wrapper as the service-credential store with `encrypt_plaintext_inference_files()` sweeping pre-baked plaintext files -- see [Encryption at Rest](encryption-at-rest.md)). The instance id IS the credential file stem: `load_inference_config()` synthesizes (and persists) an instance entry for every credential file that has none, of the kind named by the stem (`kind_for_credential_file()`: a key-holding kind name with an optional `-<n>` suffix, so `fireworks.json` / `fireworks-2.json` become Fireworks instances; the legacy `openrouter.json` becomes the `openrouter` instance seeded with the historical curated models (`_LEGACY_OPENROUTER_MODELS`), any other stem an empty OpenRouter instance) -- which is also how the local-mode dev-config `inference_credentials` pre-baking works (see [Run Modes](run-modes.md)). Deleting an instance deletes its credential file too, otherwise the next load would resurrect it.

Because `get_available_models()` re-reads the config, the credential store and the health store on every call, every save takes effect without a restart.

### OpenRouter catalog cache

`chat/llm/openrouter_catalog.py` fetches `https://openrouter.ai/api/v1/models` (public, no key) and caches the normalized list (`id`, `name`, `context_length`, `top_provider.max_completion_tokens`, per-token prices converted to $/1M) in `DATA_DIR / "openrouter_catalog.json"` for 24 hours. `get_catalog()` serves the cache while fresh, re-fetches otherwise (or on `refresh`), and on a failed fetch returns the stale cache -- or an empty list when there never was one -- with the error alongside, so the UI degrades to custom-id entry. `search_catalog()` (substring on id/name, id-prefix hits first) backs the typeahead; `catalog_snapshot()` produces the per-model snapshot on add.

### Fireworks catalog cache

`chat/llm/fireworks_catalog.py` fetches the shared `fireworks` account's model list, `GET https://api.fireworks.ai/v1/accounts/fireworks/models` (the management API, a different path prefix from the inference endpoint; `pageSize=200`, following `nextPageToken` up to `MAX_PAGES`), which requires a bearer API key -- so `get_catalog(api_key, refresh=False)` takes the instance's stored key and, with no key, reports `"No API key saved yet."` instead of fetching. Entries are normalized to the OpenRouter row shape plus `detail` / `capabilities` (like self-hosted discovery, so `search_catalog()` / `catalog_snapshot()` apply unchanged): the resource `name` is the wire id, `displayName` the name (the last path segment when absent), `contextLength` the context window, `max_completion_tokens` is always null, `capabilities` holds `tools` / `vision` from `supportsTools` / `supportsImageInput` (the typeahead flags models without `tools`), and pricing comes from the first `serverlessModes[].skuInfos` whose SKU names are matched by keyword (`... input tokens (uncached)` → `prompt`, `... input tokens (cached)` → `cache_read`, `... output tokens` → `completion`; Google `Money` `units` + `nanos` scaled by the `unit` to $/1M tokens, non-token SKUs ignored, a renamed SKU degrades to "no pricing"). Models that are not callable serverless are dropped: `state` other than `READY`, neither `supportsServerless` nor a serverless mode, or a `deprecationDate` that has passed. The normalized list is cached in `DATA_DIR / "fireworks_catalog.json"` (`FIREWORKS_CATALOG_FILE`) for 24 hours -- the catalog is the same public list for every key, so one cache serves every Fireworks instance -- with the same stale-on-failure degradation as the OpenRouter cache (HTTP errors carry the Fireworks `error.message`, e.g. the 401 for a revoked key).

### Self-hosted model discovery

`chat/llm/local_catalog.py` asks a `local` instance's server for its models -- live and uncached, since what a local box serves changes whenever a model is loaded or pulled -- and returns entries with the same keys as an OpenRouter catalog entry (plus `detail` and `capabilities` for the typeahead), so `search_catalog()` / `catalog_snapshot()` from the OpenRouter module apply unchanged:

- `openai`: `GET <base_url>/v1/models`. The `id` is what the request must name (llama.cpp: the model path or `--alias`; vLLM: the served model name; LM Studio: the model key). llama.cpp reports the loaded context size in `meta.n_ctx` (older builds only the training size `n_ctx_train`, with `GET /props` `default_generation_settings.n_ctx` as the fallback), so `context_length` is exact there and `None` (→ the conservative default) elsewhere; `detail` carries the parameter count / quantization / owner when reported.
- `ollama`: `GET /api/tags` for the pulled models (family, parameter size, quantization, and on recent versions the training context and capabilities), with `POST /api/show` (bounded to 40 lookups, 4 at a time) filling in `model_info."<arch>.context_length"` and `capabilities` for older servers. `context_length` is what the provider will request as `num_ctx`: the training size capped at `DEFAULT_OLLAMA_CONTEXT_LENGTH` (32K -- Ollama sizes the KV cache from it), editable per model afterwards. A model whose capabilities lack `tools` is flagged "no tool support" in the typeahead.

**Context window sizing.** This app's system prompt (tool definitions, system-skill index, workspace instructions) is roughly 17K tokens on a Qwen/Llama tokenizer before any conversation history, so a self-hosted server must allow a context of at least 32K: llama.cpp must be started with `-c 32768` (or more; a 16K server rejects the very first turn with `exceed_context_size_error`, which surfaces as the conversation's error bubble), and an Ollama model's `context_length` in the instance config -- the requested `num_ctx` -- must stay at the 32K default or higher. The Models panel of a self-hosted card says so.

Neither kind of server publishes a marketing name, so `name` is derived from the id by `friendly_name()` (`qwen2.5:0.5b` → `Qwen2.5 0.5b`, `/models/llama-3.2-3b-instruct-q4_k_m.gguf` → `Llama 3.2 3b Instruct Q4 K M`). A server that cannot be reached returns `{"models": [], "error": ...}`; `default_snapshot()` (zero pricing, the default Ollama context) covers custom ids and unreachable servers when a model is added anyway. The stored key, when present, is sent as a bearer token on every discovery request too.

## Model Health Checks (server-global)

Per-model health is **server state**, not a per-request UI probe. `ModelHealthStore` (`chat/llm/health.py`) keeps the latest verdict per (qualified) model id -- `{ok, error, checked_at}` -- in memory, mirrored atomically to `data/model_health.json` (`MODEL_HEALTH_FILE` in `config/paths.py`) so it survives restarts. At startup the quest lifespan launches `run_startup_model_checks()` as a background task: it checks every model returned by `get_configured_models()` -- enabled, credentialed, non-deprecated; so **disabled models are never checked** and an unconfigured deployment runs zero checks -- with concurrency bounded to 4 to avoid tripping per-project rate limits, then logs a summary.

The store **drives the model picker**: `get_available_models()` (what `GET /app/api/config` returns as `available_models`) is `get_configured_models()` minus every model whose latest verdict is an explicit failure. A never-checked model stays visible -- only a recorded failing check hides one, so a fresh boot or a deleted `model_health.json` can never empty the picker -- and health only filters *selection*: existing conversations and routines on an unhealthy model keep running.

Recovery paths are the startup sweep (which deliberately iterates the health-blind configured list so hidden models keep being rechecked), the admin per-model Recheck, and the automatic background recheck (`schedule_model_rechecks()`) after an instance key/model-list save or a Vertex model being re-enabled. Verdicts of models removed from an instance (or of a deleted instance) are dropped via `ModelHealthStore.forget()`.

A check is a **minimal live inference call** through the real provider instances (`check_model_access()` on each provider: 1 output token for Claude, OpenRouter, Fireworks and self-hosted servers -- on Ollama a non-streaming `/api/chat` call that also loads the model, so an out-of-memory model fails here -- a ~25-token cap for Gemini) -- deliberately not a metadata lookup, so it surfaces exactly what a real send would hit: a Claude model never enabled in Vertex Model Garden, bad key, wrong project/region, quota exhaustion. `check_model()` resolves the id with `resolve_model()` (so the right instance's provider object and key are used), wraps the call with a 45s timeout and returns failures as data with a compact extracted error (`extract_error_message()` understands both the anthropic `body.error.message` shape and google-genai's `code`/`message` attributes, truncated to 600 chars).

## Admin API

All endpoints are admin-gated (403 otherwise, incl. while impersonating) and live in `chat/routes/admin.py`:

- **GET `/admin/inference-providers`** → `{vertex, instances, kinds, api_types}`. `vertex` is the detected environment (`detail`) plus its model rows; each `instances[]` entry is `{id, kind, kind_label, label, configured, source, credentials: {api_key_set}, hint, key_required, base_url, api_type, models}` (never the key; `base_url` / `api_type` are null on OpenRouter and Fireworks instances, `key_required` is false on self-hosted ones, `configured` follows `instance_configured()`). Model rows are `{id, wire_id, display_name, family, enabled, max_input_tokens, discontinued_on, status}` with `id` the stored/qualified id, `discontinued_on` the registry's announced provider shutdown date (Vertex only, else null; the row disappears on that date) and `status` the stored verdict or null. `kinds` lists the addable instance kinds (`{kind, label, endpoint, catalog}` -- `catalog` one of `openrouter` / `fireworks` / `server`, telling the card which typeahead source to use), `api_types` the self-hosted API types (`{id, label, description}`).
- **PUT `/admin/inference-providers/vertex`** `{disabled_models}` -- full replacement of the Vertex disabled set (non-registry ids → 400 `unknown_model`); newly re-enabled configured models are rechecked in the background.
- **POST `/admin/inference-providers/instances`** `{kind, label?}` -- adds an empty instance with a server-generated id (`openrouter`, `openrouter-2`, ..., `fireworks`, `fireworks-2`, ..., `local`, `local-2`, ...; orphaned credential files count as taken); unknown kinds → 400 `unknown_kind`.
- **PUT `/admin/inference-providers/instances/{id}`** `{label?, api_key?, base_url?, api_type?, models?}` -- omitted = keep; empty `api_key` keeps the stored key (400 `invalid_params` when a key-required kind has nothing to keep and nothing else to save; on self-hosted instances an empty key is simply "no key"); `base_url` / `api_type` are accepted on self-hosted instances only (400 on the fixed-upstream kinds; malformed URL or unknown type → 400 `invalid_params`); `models` is a full-replacement `[{id, enabled, name?, context_length?}]` list of wire ids in display order, new entries snapshotted from the kind's catalog -- the cached OpenRouter catalog, the cached Fireworks catalog fetched with the instance's key, or the self-hosted server's live model list (`_catalog_snapshots()`) -- the optional `name` / `context_length` (positive) overriding the stored snapshot, removed entries' health verdicts dropped. A key or endpoint change drops cached SDK clients (an endpoint change also the cached provider object, since the API type selects the provider class); any of these changes schedules rechecks of the instance's configured models.
- **DELETE `/admin/inference-providers/instances/{id}`** -- removes the config entry, the credential file, the cached provider object and the models' verdicts. Conversations referencing its models keep their ids and fail at their next send with a clear not-configured error, like after a revoked key.
- **GET `/admin/inference-providers/openrouter/catalog?q=&limit=&refresh=`** -- typeahead candidates `{models, fetched_at, stale, error}` from the shared OpenRouter catalog.
- **GET `/admin/inference-providers/instances/{id}/catalog?q=&limit=&refresh=`** -- an instance's OWN catalog, `{models, error}`: for a self-hosted instance the models its server reports right now (live, uncached; `error` set with an empty list when the server is unreachable or no URL is saved yet; `refresh` ignored), for a Fireworks instance the cached serverless catalog fetched with the instance's stored key (`refresh=true` re-fetches; no key saved yet → `{"models": [], "error": "No API key saved yet."}` without a fetch; a rejected key → the stale cache or an empty list with the HTTP error); 400 on OpenRouter instances, whose typeahead is the shared route above.
- **POST `/admin/inference-providers/test-model`** `{model}` → `{model, ok, error, checked_at}` -- live recheck that updates the store (unknown → 404, disabled → 400 `model_disabled`; a bare legacy OpenRouter id is recorded under its qualified id).

## Frontend

`frontend/src/components/settings/InferenceProvidersSection.tsx` renders the Vertex card (environment info + a Models panel grouped into the `anthropic` / `gemini_vertex` families), one card per instance (editable label, write-only API key with keep-on-empty -- marked optional on self-hosted cards --, on self-hosted cards a Server URL field and an API type selector with the type's one-line description, a Models panel with a remove `×` per row and the "Add model" combobox `AddModelCombobox` -- debounced search over the kind's `catalog` source: the shared OpenRouter catalog, or the instance's own catalog via `searchInstanceCatalog()` (the self-hosted server's live list, or the Fireworks catalog; disabled until the server URL / API key is saved, per-source placeholder copy from `addModelCopy()`), keyboard navigation, a "use as a custom model id" row when the typed id is not listed or the list is unavailable, "no tool support" noted on Ollama and Fireworks models lacking the capability; Fireworks cards carry a note about the `accounts/fireworks/models/<name>` id form and typing a dedicated deployment id in as a custom id), and the footer add buttons (one per `kinds` entry). Self-hosted model rows additionally show the inline `ModelEditFields` editor (display name + context window in tokens, saved on blur/Enter through the same full-replacement `models` PUT with `name` / `context_length` overrides). Every model row is `[checkbox] wire_id  display name  ● [Recheck]`: the checkbox saves immediately (Vertex: the disabled set; instance: the full model list), the dot is grey / green / red for never-checked / responding / failing (a spinner while checking, the extracted error inline under a failing row; a Vertex model with a `discontinued_on` date gets a muted "Discontinued on <date> -- then hidden from pickers" line), and both the dot and Recheck are hidden while the model is disabled or its provider is unconfigured. "Recheck all" covers only enabled, configured models. API types are in `frontend/src/api/types.ts`, client functions in `frontend/src/api/client.ts`.

## Adding a Provider Kind

A kind is an `INSTANCE_KINDS` entry naming its LLMProvider implementation, analytics backend label, key requirement, whether it carries its own endpoint (else its fixed `upstream_url`) and its `catalog` source, plus a `get_provider_instance()` branch constructing that provider with the instance id. The stores, the admin endpoints, the settings cards and the add-button footer are all driven by the registry; the `local` kind is the worked example of an endpoint-carrying kind (extra instance fields normalized in `_normalize_instance()`, accepted by the PUT body, rendered by `InstanceCard` when the kind's `endpoint` flag is set), and `fireworks` the worked example of a fixed-upstream, key-required kind with its own catalog module -- any other OpenAI-compatible hosted API (Together, Groq, a direct OpenAI key…) follows the same recipe: a registry entry with the upstream URL, a catalog module producing the shared row shape (or `catalog: "openrouter"`-style reuse of an existing one), and a branch in `_catalog_snapshots()` / `admin_instance_catalog`.

## Design Decisions

**Why qualified model ids instead of a separate instance column?**
The model id is already the universal key -- conversation and routine rows, per-user defaults, the health store, analytics rows, the frontend catalog -- so folding the instance into it keeps every one of those paths unchanged and the migration a pure string prefix. A separate column would have had to be threaded through the WebSocket send path, the scheduler, sub-agent spawning and analytics.

**Why snapshot catalog metadata instead of reading the catalog at request time?**
Sends must not depend on openrouter.ai being reachable, and pricing must stay stable for the rows already recorded. The snapshot is refreshed only when the admin adds the model again. Since the provider captures the amount OpenRouter actually charged per call (`llm_calls_openrouter.cost`, see [LLM Providers](llm-providers.md#openrouterprovider)), the snapshot only prices rows recorded before that capture existed -- drift in it no longer skews the reports.

**Why do self-hosted servers and Fireworks reuse the `openrouter` provider family instead of getting their own?**
Every local server and Fireworks speak the OpenAI chat-completions protocol, and the provider name is woven through the history envelope (`sdk_history.json`), the interruption-marker writer, the analytics table choice and the frontend usage cell. A separate `local` or `fireworks` provider would have duplicated all of that for an identical message format. The kind's `backend` label (`local` / `fireworks`) is what distinguishes the rows in cost reports; the instance label is folded into the model's display name in pickers ("Qwen2.5 0.5b (Ollama box)"), so users still see where a model runs.

**Why a direct Fireworks kind when OpenRouter already routes to Fireworks?**
A direct key skips the OpenRouter markup and routing, keeps traffic inside one vendor agreement (data-handling terms, invoicing) and reaches dedicated deployments (`accounts/<account>/deployments/<id>`), which OpenRouter cannot address. Fireworks' catalog needs a key to read, which is why its typeahead is a per-instance route (fetched with the saved key) rather than the public OpenRouter one; one cache still serves every Fireworks instance because the public list is the same for every key.

**Why a native Ollama transport rather than Ollama's OpenAI-compatible endpoint?**
The compatibility endpoint cannot set the context window: Ollama runs every model at a small default (its startup log on a GPU-less box says `default_num_ctx=4096`) and silently truncates the prompt, which for this app means the system prompt's tool instructions are the first thing to go. The native `/api/chat` takes `options.num_ctx` per request. The transport is a subclass that only swaps the wire format, so history, repair and analytics stay shared. Ollama's official workaround (a derived model with `PARAMETER num_ctx` in a Modelfile) would push a per-app concern onto every admin.

**Why is self-hosted pricing an explicit $0 instead of "unknown"?**
A null price makes every report that includes the model show no total at all (the "no estimate" rule protects against under-reporting an unpriced paid model). A self-hosted model has no per-token charge, so zero is the honest figure and keeps the deployment's other spend visible; the row is still tagged `estimated`, and an admin who wants to reflect hardware cost can leave the number at zero and read the token columns.

**Why is self-hosted model discovery not cached, while the OpenRouter and Fireworks catalogs are?**
The OpenRouter and Fireworks catalogs are public lists of hundreds of entries that change daily and cost a remote request; a local box's list changes whenever the admin loads or pulls a model and is a single fast LAN request. Caching it would only make the typeahead lie right after `ollama pull`.

**Why is Vertex read-only in the panel?**
Vertex auth is ambient (ADC/env), typically provisioned by `run.py`, the prod bootstrap, or deployment tooling, and consumed by Google SDKs outside the app's control; the panel's job is to make the detected state visible, not to own it. Metadata-server credentials (GCE instance service accounts) are intentionally not probed to keep the settings request free of network calls, and the card says so. Enabling/disabling individual Vertex models is app state, so that part is editable.

**Why a store separate from `service_credentials/`?**
Inference providers are not upstream data integrations: they have their own instance registry, a different form shape (bare API key vs OAuth client), and their own settings section. Sharing the directory would leak them into the Service Credentials list endpoint, which iterates `KNOWN_SERVICES`. The file format and atomic-write scheme are deliberately identical.

**Why is the API key write-only with empty-means-keep?**
Same reasoning as service credentials: the browser never needs the key back, and an empty save keeps the stored key -- see [Service Credentials](service-credentials.md).
